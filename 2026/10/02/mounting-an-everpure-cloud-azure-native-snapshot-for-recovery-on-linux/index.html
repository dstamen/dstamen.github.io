Mounting an Everpure Cloud Azure Native Snapshot for Recovery on Linux

October 2, 2026 · 9 min read · 1882 words
Share

Are you looking for a way to get a few files back from an Everpure Cloud Azure Native snapshot without overwriting the live volume? The portal gives you two options today: overwrite the volume group, or restore the snapshot into a brand new volume group. Overwrite is destructive, and a new volume group means a new iSCSI target to mount on the VM. What I usually want is the old copy of one volume mounted next to the current one, so I can copy back what I need and throw the copy away. So I wrote a script that does exactly that. I started with Linux, and in Part 2 I do the same thing on Windows.

Disclaimer: this is a proof of concept, not an officially supported pattern. I validated it end to end on Ubuntu 24.04 against a live pool in West US 2, but the error handling is lab-grade. Treat it as a working example to build your own version from.

How It Works#

You give it a VM, a volume, and optionally a mountpoint. It does the rest:

  1. Finds the volume group with the same name as the VM. It searches every storage pool in the subscription unless you pass one.
  2. Picks the newest snapshot that isn’t destroyed and actually contains the volume.
  3. Clones that volume’s member snapshot into a new volume called <volume>-restored, in the same volume group.
  4. Waits until the clone has a serial number.
  5. Uses Run Command to rescan iSCSI in the guest, find the new LUN, and mount it at the source mountpoint plus -restored.

The clone lands in the volume group the VM is already logged in to. That’s the trick that keeps this simple. The MountIscsiLinux extension doesn’t change at all, the guest just needs a rescan to see a new LUN on the target it already has.

The VM name to volume group name mapping is just how my lab is set up. If yours is different, that lookup is the one thing to change.

Prerequisites#

  • An Everpure Cloud Azure Native volume group already mounted on a Linux VM through MountIscsiLinux
  • At least one snapshot of that volume group, manual or from a protection policy
  • The Azure CLI , logged in, and jq
  • The VM running, since Run Command needs the guest agent

The complete code is available as a zip . It’s two files in linux/, ec-restore.sh runs on your workstation and guest-mount.sh gets sent to the VM.

Picking the Snapshot#

Volume group snapshots are taken across every volume in the group, and each one holds a member snapshot per volume, named after the volume. The catch is that the list call doesn’t return those members, only a single GET does. A volume that was added after a snapshot was taken won’t be in it either. So the script walks from newest to oldest and stops at the first one that has the volume:

CANDIDATES=$(az rest --method get --url "$ARM$VG_ID/snapshots?api-version=$SNAP_API" |
  jq -r '[.value[] | select(.properties.softDeletion.destroyed != true)]
         | sort_by(.properties.createdAt) | reverse | .[].name')

for s in $CANDIDATES; do
  body=$(arm_get "$VG_ID/snapshots/$s?api-version=$SNAP_API")
  if echo "$body" | jq -e --arg v "$VOL" '.properties.volumeSnapshots[]? | select(.name == $v)' >/dev/null; then
    SNAP_ID="$VG_ID/snapshots/$s"
    break
  fi
done

Policy snapshots and manual ones come back in the same list and restore the same way, so a protection policy on the volume group just gives you more to choose from.

Latest or a Specific One#

The latest snapshot is the default because it’s usually what you want. Someone deleted a folder an hour ago, the newest snapshot from before that has it, and you lose the least.

It’s the wrong choice when the damage is older than the last snapshot. With an hourly policy the newest snapshot can be from ten minutes ago, and if a bad deploy, a corrupted database or ransomware got in before that, the latest copy has the problem too. That’s when you go back and pick one.

To see what you have, list the snapshots with their times and whether a policy took them:

az rest --method get --url "https://management.azure.com<vg-id>/snapshots?api-version=2026-05-01-preview" \
  --query "sort_by(value[?properties.softDeletion.destroyed==\`false\`], &properties.createdAt)[].{name:name, created:properties.createdAt, policy:properties.createdByPolicy}" -o table

Name    Created                    Policy
------  -------------------------  --------
1       2026-10-01T14:38:30+00:00  True
adhoc   2026-10-01T14:40:20+00:00  False
4       2026-10-01T15:38:30+00:00  True
5       2026-10-01T16:38:30+00:00  True
6       2026-10-01T17:38:30+00:00  True

Policy snapshots get numbered names, manual ones keep whatever you called them. Pick the last one from before the problem started and pass it with -s:

./linux/ec-restore.sh -g <rg> -n app-vm01 -v data1 -s 5 -r -d

With -s the script doesn’t walk back to older snapshots. If that snapshot doesn’t hold the volume it stops and tells you. Run it with -d first to confirm which snapshot it resolved, then again without it.

If you’re not sure which one is clean, restore a couple of them at once with different suffixes (-x -restored-5, -x -restored-4) and compare. Each one is a separate volume, so they don’t get in each other’s way.

Cloning the Volume#

The clone is a normal volume PUT with a source. No provisionedSize, the clone takes the size the member snapshot was taken at:

BODY=$(jq -nc --arg vg "$VG_ID" --arg snap "$SNAP_ID" --arg vol "$VOL" '{properties: {
  sourceType: "snapshot",
  sourceVolumeGroupResourceId: $vg,
  sourceVolumeSnapshot: {volumeGroupSnapshotResourceId: $snap, volumeSnapshotName: $vol}}}')

az rest --method put --url "$ARM$VG_ID/volumes/$NEW_VOL?api-version=$VOL_API" --body "$BODY"

Volumes don’t report a provisioningState, so the script polls the GET until it has a serialNumber. The serial is what the guest uses to find the LUN.

Mounting It in the Guest#

The guest side goes through Run Command with the serials passed as parameters:

az vm run-command invoke -g "$RG" -n "$VM" --command-id RunShellScript \
  --scripts @guest-mount.sh \
  --parameters "$NEW_SERIAL" "$SRC_SERIAL" "$MNT" "$MODE" "$NEW_VOL"

Everpure volumes show up in Linux with a WWID of 3624a9370 plus the serial in lowercase, so after a rescan the script can go straight to /dev/disk/by-id/dm-uuid-mpath-3624a9370<serial> without guessing which sdX is which.

Two filesystem things matter here. A clone has the exact same filesystem UUID as its source, and XFS refuses to mount a second filesystem with a UUID that’s already mounted. So XFS clones get mounted with nouuid. ext4 doesn’t care. LVM is the other one. A cloned PV carries the same PV and VG UUIDs as the original, so the script stops and tells you to use vgimportclone instead of trying to be clever.

If you don’t pass a mountpoint, it finds where the source volume is mounted and adds -restored, so /data gets its copy at /data-restored. Nothing goes into /etc/fstab, the copy is meant to be temporary.

Testing It#

To make sure I was getting a true point-in-time copy, I set up a fresh VM with its own volume group and a 10 GiB volume, formatted XFS and mounted at /mnt/data1. I wrote a marker file and a 64 MiB file of random data, took a manual snapshot, waited until the snapshot actually existed, then wrote a second marker file to the live volume.

Then I ran the restore read-only:

./linux/ec-restore.sh -g <rg> -n app-vm01 -v data1 -r

==> source volume: data1 (serial A1B2C3D4E5F6A7B800011578)

And the copy has exactly what was there at snapshot time:

orig:     after-snap.txt before-snap.txt blob
restored: before-snap.txt blob
55cd351caff944c16fb5c9ac3b942aa5e9942e21f0f8af9d0f438b89a40ff5da  /mnt/data1-restored/blob

The marker written after the snapshot isn’t in the copy, the checksum on the random file matches the original, and both the original and the clone have all four paths up.

Things That Bit Me#

Snapshot create is asynchronous. ARM accepts the snapshot PUT before the array actually takes it. On one run it landed 23 seconds after the accept, and the file I wrote “after” the snapshot ended up inside it. If you’re scripting snapshot-then-write, wait until a GET on the snapshot returns a createdAt before you touch the data.

A dead path can hang Run Command for a long time. The multipath maps use queue_if_no_path, so any read against a map with no live path just blocks. I hit this once in the lab when a volume group lost its paths, and the Run Command doing the mount sat there. Legacy Run Command only runs one at a time per VM, and a stuck one holds up other VM operations, a restart included, until it times out after 90 minutes. The guest script now waits for an active ready running path before it reads the disk at all, and puts a timeout on everything that touches it.

Checking what Run Command did. The legacy Run Command has no status object you can query. The useful places are the activity log for the run history, and inside the guest each run keeps its script and output under /var/lib/waagent/run-command/download/<n>/. If the guest is unreachable, az vm boot-diagnostics get-boot-log still shows kernel messages like alua: rtpg failed, which is usually the first sign a LUN went away.

Cleaning Up#

Once you’ve copied back what you need, the clone has to come out of the guest before it gets deleted in Azure. The order matters here.

If you only unmount it and then delete the volume, the multipath map and its four sd paths stay behind, pointing at a LUN that no longer exists. Because the maps use queue_if_no_path, anything that reads that map later can hang. That’s blkid, an LVM scan, lsblk, even udev. It’s the same thing as the stuck Run Command above, just delayed until something trips over it.

So there are two steps, in this order.

1. In the guest, through Run Command. Unmount the clone, flush its multipath map, and remove each path device. The WWID is 3624a9370 plus the clone’s serial in lowercase. The serial is in the restore script’s output:

az vm run-command invoke -g <rg> -n app-vm01 --command-id RunShellScript --query "value[0].message" -o tsv --scripts '
W=3624a9370<serial>
umount /mnt/data1-restored
DM=$(basename "$(readlink -f /dev/mapper/$W)")
PATHS=$(ls /sys/block/$DM/slaves)
multipath -f $W
for d in $PATHS; do echo 1 > /sys/block/$d/device/delete; done
[ -z "$(multipath -ll $W)" ] && echo "map removed"'

The path list gets read before the flush, because once the map is gone there’s nothing left to look it up from.

2. From your workstation or jumpbox. Delete the volume from the same place you ran ec-restore.sh. It’s an ARM call, so it doesn’t run in the guest:

az rest --method delete --url "https://management.azure.com<vg-id>/volumes/data1-restored?api-version=2026-05-01-preview"

There’s no rescan needed afterward. The guest already let go of the LUN in step 1.

The delete is a soft delete, so the volume sits in the recoverable state for a while before it’s eradicated.

If you already deleted it first. The map will show its paths as failed. Tell it to stop queuing, then flush it and remove the paths the same way:

dmsetup message 3624a9370<serial> 0 fail_if_no_path
multipath -f 3624a9370<serial>
