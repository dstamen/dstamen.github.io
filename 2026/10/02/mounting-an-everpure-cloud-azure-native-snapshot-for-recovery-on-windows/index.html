Mounting an Everpure Cloud Azure Native Snapshot for Recovery on Windows

October 2, 2026 · 7 min read · 1450 words
Share

Are you running Windows VMs on Everpure Cloud Azure Native and need a few files back from a snapshot without touching the live volume? In Part 1 I cloned one volume from the latest volume group snapshot and mounted it next to the original on Linux. This time it’s Windows. The Azure side is exactly the same, the guest side is where Windows does its own thing.

Disclaimer: this is a proof of concept, not an officially supported pattern. I validated it end to end on Windows Server 2025 against a live pool in West US 2, but the error handling is lab-grade. Treat it as a working example to build your own version from.

What Changes on Windows#

Finding the volume group, picking the snapshot and cloning the volume are the same API calls as Part 1, so I won’t repeat them here. Everything in Picking the Snapshot applies, including going back to an older snapshot with -Snapshot when the latest one already has the problem.

What’s different is what happens once the clone shows up in the guest:

LinuxWindows
Finding the cloneWWID 3624a9370 + serialGet-Disk serial number
Duplicate IDXFS needs nouuiddisk held offline as a GUID collision
Where it mountssource mountpoint + -restorednext free drive letter, or a folder

The workstation script is PowerShell this time too. It needs PowerShell 7, so it runs fine from a Mac or Linux box as well. I ran all of this from my Mac.

Prerequisites#

  • An Everpure Cloud Azure Native volume group already mounted on a Windows VM through MountIscsiWindows, with MPIO installed
  • At least one snapshot of that volume group, manual or from a protection policy
  • PowerShell 7 and the Azure CLI , logged in
  • The VM running, since Run Command needs the guest agent

The complete code is available as a zip . It’s two files in windows/, ec-restore-windows.ps1 runs on your workstation and guest-mount.ps1 gets sent to the VM through RunPowerShellScript.

Running It#

./windows/ec-restore-windows.ps1 -ResourceGroup <rg> -VmName app-win01 -Volume data1 -ReadOnly

-MountPath takes a drive letter like R: or an empty folder like C:\restored\data1. Leave it off and you get the next free drive letter. -DryRun resolves the volume group, volume and snapshot and stops, same as -d on Linux.

Finding the Disk#

Windows shows the Everpure serial number directly on the disk, so there’s no WWID to build. After a rescan the guest script just matches on it:

Update-HostStorageCache
$disk = Get-Disk | Where-Object SerialNumber -eq $NewSerial

Before it touches the disk it checks MPIO has paths to it. MPIO reports the LUN by its NAA id, which is 624A9370 plus the serial:

$mpio = Get-CimInstance -Namespace root/wmi -ClassName MPIO_DISK_INFO |
  ForEach-Object { $_.DriveInfo } | Where-Object { $_.SerialNumber.Trim() -eq "624A9370$NewSerial" }

A healthy volume shows four paths, two Active/Optimized and two Active/Unoptimized.

The Clone Comes Up Offline#

This is the big one on Windows. A clone is a block for block copy, so it has the exact same disk GUID as its source. Windows won’t run two disks with the same GUID, so it leaves the clone offline with an OfflineReason of Collision.

Bringing it online fixes that. Windows writes a new GUID to the clone on the way up:

Set-Disk -Number $disk.Number -IsOffline $false

brought online (offline reason: Collision); guid {c0d5ab43-146e-481c-ae2e-7f51d1b3e15e} -> {3d52f3df-bdcc-11f1-854d-000d3ac33b68}

It’s the same problem as XFS and nouuid in Part 1, Windows just handles it at the disk level. MBR disks hit the same thing with the disk signature.

Read-only adds a wrinkle. Writing the new GUID is a write, so a disk that’s already read-only can’t take it. The script clears read-only just long enough to bring the disk online, then sets it right back before anything mounts it.

Picking Where It Mounts#

Windows may hand the partition a drive letter on its own when it comes online. With no -MountPath the script keeps that letter, or assigns the next free one if there isn’t one.

A letter like R: moves it there. A folder path mounts it as a mount point inside an existing NTFS volume, which is handy when you’re running out of letters or want the restore to sit next to the data it came from.

Don’t hardcode a letter in your own version. On a fresh Azure VM E: was already taken by the CD-ROM.

What It Stops On#

Dynamic disks and Storage Spaces. These are the Windows version of LVM in Part 1. A cloned member collides with the source pool or disk group, so the script stops and tells you to import it by hand instead of guessing.

BitLocker. A locked volume shows no filesystem, so the script stops and says so. Unlock it with the recovery key and mount it yourself.

Testing It#

I set up a fresh Windows Server 2025 VM with its own volume group and a 10 GiB volume, formatted NTFS on F:. Same test as Part 1: a marker file and a 64 MiB file of random data, then a manual snapshot, wait until the snapshot actually exists, then a second marker file on the live volume.

Then the restore, read-only:

And the copy has exactly what was there at snapshot time:

The marker written after the snapshot isn’t there, the checksum matches, G: refuses writes, and F: is untouched. Both disks show four MPIO paths. I also ran it a second time with -MountPath C:\restored\data1 and no -ReadOnly, and got the same files mounted read-write in the folder.

Things That Bit Me#

Run Command parameters can’t start with a dash. On Windows, Run Command passes each parameter to the script as -Name value. My first version used - to mean “pick a letter for me”, and the handler failed before the script even ran with an error about the argument “name” not being valid. The default is auto now.

MountIscsiWindows reboots to finish MPIO. On a fresh VM I set reboot: true so the extension could install MPIO. Right after the reboot there were zero iSCSI sessions. The extension does a second pass once the VM is back up, and the sessions showed up about a minute and a half later. If you check too early it looks broken.

Run Command splits stdout and stderr on Windows. Linux gives you one message with both in it. Windows returns two, StdOut and StdErr, so if you only read the first one a failure just looks like the script stopped halfway. The workstation script prints both.

Cleaning Up#

Same idea as Part 1. Take the clone out of the guest first, then delete it in Azure. Windows is more forgiving than Linux if you get the order wrong, but doing it this way keeps a dead disk from sitting in Disk Management.

1. In the guest, through Run Command. If you mounted it in a folder, remove the mount point first. Then take the disk offline. Matching on the serial means you don’t need to know the disk number:

az vm run-command invoke -g <rg> -n app-win01 --command-id RunPowerShellScript --query "value[].message" -o tsv --scripts '
$d = Get-Disk | Where-Object SerialNumber -eq "<serial>"
Get-Partition -DiskNumber $d.Number | Where-Object AccessPaths -contains "C:\restored\data1\" |
  Remove-PartitionAccessPath -AccessPath "C:\restored\data1\"
Set-Disk -Number $d.Number -IsOffline $true
"disk $($d.Number) offline"'

Skip the Remove-PartitionAccessPath line if it’s on a drive letter. Taking the disk offline drops the letter.

2. From your workstation or jumpbox. Delete the volume from the same place you ran ec-restore-windows.ps1:

az rest --method delete --url "https://management.azure.com<vg-id>/volumes/data1-restored?api-version=2026-05-01-preview"

3. Optional rescan. MPIO drops the dead paths on its own after PDORemovePeriod, which was 120 seconds on my VM. Until then the disk can still show up as failed. A rescan clears it right away:

az vm run-command invoke -g <rg> -n app-win01 --command-id RunPowerShellScript --scripts 'Update-HostStorageCache'

If you mounted it in a folder, delete the empty folder afterward. The volume delete is a soft delete, same as Part 1.
