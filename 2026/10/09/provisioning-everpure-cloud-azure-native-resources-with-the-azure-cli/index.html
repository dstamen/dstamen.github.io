Provisioning Everpure Cloud Azure Native Resources with the Azure CLI

October 9, 2026 · 6 min read · 1259 words
Share

I already walked through this with Terraform , provisioning an Everpure Cloud Azure Native storage pool, volume group, and volume, then mounting it to an Azure VM over iSCSI. Not everyone wants a Terraform state file for a one-off pool, so here is the same example with nothing but the Azure CLI.

Why the CLI Version#

There is actually a dedicated az pscloud extension for this, and I am using it everywhere it reaches. Right now that is reservations and storage pools only, az pscloud list, az pscloud show, and the az pscloud pool group for create, update, delete, and status. Volume groups and volumes are not covered yet. I am told that is coming, not that it is staying this way, but today those two still go through az resource create and az resource invoke-action against the generic ARM API, the same thing azapi is doing under the hood in the Terraform version. Nothing here is a workaround, it is the same API either way, just without a state file to manage.

Prerequisites#

Same requirements as the Terraform version:

  • An active Everpure Cloud Reservation in your Azure subscription
  • An existing VNet and subnet delegated to the service for storage pool injection
  • An Azure VM (Linux or Windows) that will consume the volume
  • The PureStorage.Block resource provider registered
  • The pscloud Azure CLI extension, installed automatically the first time you run az pscloud
  • jq installed locally, for pulling values back out of the CLI’s JSON output
az provider register --namespace PureStorage.Block

Setting Variables#

Put the values you will reuse across commands at the top, so nothing is typed twice:

SUBSCRIPTION_ID="<subscription-id>"
RESOURCE_GROUP="<resource-group>"
LOCATION="<location>"
RESERVATION_ID="<reservation-resource-id>"
SUBNET_ID="<subnet-id>"
VNET_ID="<vnet-id>"
ZONE="<availability-zone>"
BANDWIDTH=800
POOL_NAME="<pool-name>"
VG_NAME="<volume-group-name>"
VG_IOPS_LIMIT=50000
VOL_NAME="<volume-name>"
VOL_SIZE_BYTES=107374182400 # 100 GiB
VM_NAME="<vm-name>"
OS_TYPE="linux" # or windows

API_VERSION="2026-01-01-preview" # only needed for volume groups and volumes, pscloud handles its own

az account set --subscription "$SUBSCRIPTION_ID"

Provisioning the Reservation#

This is the one step with no CLI command at all, pscloud can list and show reservations, but not create one. The Reservation comes from the Azure Marketplace, not the command line:

  • In the Azure Portal search bar, search for Everpure and select the Azure Native Everpure Cloud Service.
  • Click Create, and on the Basics tab fill in the subscription, resource group, a name, the region, and a billing plan, On-Demand, 1 Year, or 3 Year Capacity.
  • Fill in company details, then Review + create.

That takes a minute or two. Once it exists, pscloud can find it for you instead of copying the resource ID out of the portal:

az pscloud list --resource-group "$RESOURCE_GROUP"

Grab the id field from the output and set RESERVATION_ID to it.

Provisioning the Storage Pool#

This is one of the two steps that has a real, first-class command. az pscloud pool create takes the same properties as the Terraform version, vnetInjection for the subnet and VNet, availabilityZone, and reservationResourceId, just as named flags instead of a JSON body:

az pscloud pool create \
  --resource-group "$RESOURCE_GROUP" \
  --storage-pool-name "$POOL_NAME" \
  --location "$LOCATION" \
  --zone "$ZONE" \
  --subnet-name "$SUBNET_ID" \
  --vnet-name "$VNET_ID" \
  --provisioned-bandwidth "$BANDWIDTH" \
  --reservation-id "$RESERVATION_ID"

It blocks until the operation finishes by default, and storage pool create can take up to 90 minutes. That is the CLI equivalent of the timeouts block in the Terraform version, there is nothing to configure, the CLI just waits. Add --no-wait if you would rather get your shell back and poll separately with az pscloud pool show.

Creating the Volume Group and Volume#

This is where pscloud runs out, there is no az pscloud volume-group or az pscloud volume yet. Back to az resource create for both. The volume group hangs off the pool with --parent:

az resource create \
  --resource-group "$RESOURCE_GROUP" \
  --namespace PureStorage.Block \
  --parent "storagePools/$POOL_NAME" \
  --resource-type volumeGroups \
  --name "$VG_NAME" \
  --api-version "$API_VERSION" \
  --location "$LOCATION" \
  --properties "{}"

I am leaving performanceParameters out entirely here, which lets the volume group use whatever bandwidth and IOPS the pool has available rather than capping it. If you do want a hard ceiling on this group specifically, set --properties to this instead, using the $BANDWIDTH and $VG_IOPS_LIMIT variables from earlier:

--properties "{
  \"performanceParameters\": {
    \"bandwidthLimitMbPerSec\": $BANDWIDTH,
    \"iopsLimit\": $VG_IOPS_LIMIT
  }
}"

The volume nests one level deeper, under the volume group, with the size specified in bytes:

az resource create \
  --resource-group "$RESOURCE_GROUP" \
  --namespace PureStorage.Block \
  --parent "storagePools/$POOL_NAME/volumeGroups/$VG_NAME" \
  --resource-type volumes \
  --name "$VOL_NAME" \
  --api-version "$API_VERSION" \
  --properties "{
    \"provisionedSize\": $VOL_SIZE_BYTES
  }"

Mounting the Volume to a VM#

listConnectionParameters is a POST action on the volume group, not a plain read, so there is no az resource show for it. az resource invoke-action is the CLI’s way of calling an action on an ARM resource that is not a create, update, or delete:

VG_ID=$(az resource show \
  --resource-group "$RESOURCE_GROUP" \
  --namespace PureStorage.Block \
  --parent "storagePools/$POOL_NAME" \
  --resource-type volumeGroups \
  --name "$VG_NAME" \
  --query id -o tsv)

CONN_PARAMS=$(az resource invoke-action \
  --action listConnectionParameters \
  --ids "$VG_ID" \
  --api-version "$API_VERSION")

Pull the two controllers’ IPs and IQNs back out with jq:

CT0_IP=$(echo "$CONN_PARAMS" | jq -r '.iscsi.endpoints[0].ip')
CT0_IQN=$(echo "$CONN_PARAMS" | jq -r '.iscsi.endpoints[0].iqn')
CT1_IP=$(echo "$CONN_PARAMS" | jq -r '.iscsi.endpoints[1].ip')
CT1_IQN=$(echo "$CONN_PARAMS" | jq -r '.iscsi.endpoints[1].iqn')

With those in hand, build the extension settings and hand them to az vm extension set. Unlike the pieces above, VM extensions are a first-class az command, no generic-resource workaround needed:

if [ "$OS_TYPE" = "windows" ]; then
  EXT_NAME="MountIscsiWindows"
  REBOOT_FIELD=", \"reboot\": true"
else
  EXT_NAME="MountIscsiLinux"
  REBOOT_FIELD=""
fi

SETTINGS="{
  \"targets\": [
    {\"ip\": \"$CT0_IP\", \"port\": 3260, \"iqn\": \"$CT0_IQN\"},
    {\"ip\": \"$CT1_IP\", \"port\": 3260, \"iqn\": \"$CT1_IQN\"}
  ],
  \"replaceTargets\": false,
  \"sessionCount\": 2$REBOOT_FIELD
}"

az vm extension set \
  --resource-group "$RESOURCE_GROUP" \
  --vm-name "$VM_NAME" \
  --publisher PureStorage.Extensions \
  --name "$EXT_NAME" \
  --version 1.2 \
  --settings "$SETTINGS"

Same two notes that applied to the Terraform version still apply here: the extension opens two iSCSI sessions by default, one per controller, and Windows needs reboot: true because the iSCSI initiator service has to restart to pick up the new targets.

Verifying the Mount#

To verify the iSCSI session is active on a Linux VM:

iscsiadm -m session

On Windows, from PowerShell:

Get-IscsiSession

Things Worth Knowing#

pscloud only covers reservations and storage pools today. Volume groups and volumes still go through generic az resource commands. Check the az pscloud reference before you copy this, those two gaps are the kind of thing that gets filled in without much notice.

az resource create is not idempotent the way Terraform apply is. Run it twice with the same name and you will get an error on the second run instead of a no-op. Check for existence first with az resource show if the script needs to be safely re-runnable.

Pin the API version in one place. Same advice as the Terraform version, just a shell variable instead of a Terraform local. PureStorage.Block is still moving, and you want changing it to be a single edit.

What’s Next#

If this is more than a one-off and you are going to be managing these resources on an ongoing basis, the Terraform version is the better fit, state and plan output both earn their keep once you are not just creating things once and walking away.
