Attaching Everpure Cloud Azure Native Storage to Azure Red Hat OpenShift

October 6, 2026 · 9 min read · 1741 words
Share

Previously, I deployed an Azure Red Hat OpenShift (ARO) cluster with Terraform , into an existing VNet with its own dedicated subnets. That gives you a working cluster, but the persistent storage still has to come from somewhere. This time I am provisioning Everpure Cloud Azure Native volume groups for the cluster, and pulling the iSCSI connection parameters back out of the API, which is the piece this post is really about.

The Storage Model#

Everpure Cloud Azure Native surfaces block storage under the PureStorage.Block resource provider, so everything is a native Azure resource. I covered the resource model in more detail in provisioning Everpure Cloud Azure Native resources with Terraform , but the short version is:

  • Reservation: the top-level container tied to your subscription, which handles billing
  • Storage Pool: injected into a delegated subnet in your VNet, pinned to an availability zone
  • Volume Group: a logical grouping equivalent to a host or workload, where bandwidth and IOPS limits are set
  • Volume: the block device itself

For ARO I create one volume group per node, but only for the workers that need storage, not every node in the cluster. That gives each of those nodes its own bandwidth and IOPS envelope, and it keeps the connection parameters separate so you can attach them independently.

Put the storage pool in the same VNet as the cluster. It keeps traffic on VNet-local routing and avoids paying peering charges on every I/O.

Worth being clear about which layer this post is at. Everpure Cloud on ARO is officially supported now , and the announced path runs through Portworx: storage classes and PVCs handle the Kubernetes side, and Everpure Cloud sits underneath as the storage foundation. What follows here is one level down from that. I am wiring up the volume groups directly with Terraform and pulling the iSCSI endpoints out as outputs, which is the piece Portworx (or a follow-up post, if you are doing this by hand) would consume next.

Prerequisites#

On top of everything already in place from deploying the cluster:

  • An active Everpure Cloud Reservation in your subscription
  • An existing storage pool, in the same VNet as the cluster
  • The PureStorage.Block resource provider registered
  • The azure/azapi provider added alongside azurerm
  • Your region is on the supported list
az provider register --namespace PureStorage.Block

Adding the azapi Provider#

azurerm does not have a resource for the volume group API yet, and that is normal, not a sign of anything wrong. Azure ships new resource providers and API versions faster than any Terraform provider can track them, PureStorage.Block being on a preview version right now is just this case of that. The azapi provider exists for exactly this gap: it talks directly to the Azure ARM REST API, so you can manage a resource type the moment it exists, preview or not.

terraform {
  required_providers {
    azapi = {
      source = "azure/azapi"
    }
    azurerm = {
      source = "hashicorp/azurerm"
    }
  }
}

provider "azapi" {
  subscription_id = var.subscription_id
}

Then build the resource IDs once in locals.tf rather than repeating them:

locals {
  api_version     = "2026-01-01-preview"
  storage_pool_id = "/subscriptions/${var.pool_subscription_id}/resourceGroups/${var.pool_resource_group}/providers/PureStorage.Block/storagePools/${var.pool_name}"
}

Pinning api_version in one place matters more than it looks. The PureStorage.Block API is still moving, and when the version changes you want that to be a single edit rather than a search and replace.

Provisioning the Volume Groups#

I use for_each over a set of names so the number of volume groups tracks the worker count:

locals {
  volume_groups = toset(["aro-worker-1", "aro-worker-2", "aro-worker-3"])
}

resource "azapi_resource" "volume_group" {
  for_each = local.volume_groups

  type                      = "PureStorage.Block/storagePools/volumeGroups@${local.api_version}"
  name                      = each.key
  location                  = var.location
  parent_id                 = local.storage_pool_id
  tags                      = var.tags
  schema_validation_enabled = false

  body = {
    properties = {}
  }

  response_export_values = ["*"]
}

Two lines there are doing real work.

schema_validation_enabled = false is required. The provider has no embedded schema for this preview API version, so without it azapi rejects the resource before it ever sends the request.

response_export_values = ["*"] returns the full response body. You need it for the next step.

parent_id points at the existing storage pool, which is why the pool ID gets built in locals.tf. The pool can live in a different resource group or even a different subscription from the cluster. The resource ID is the only thing that has to line up.

Pulling the iSCSI Connection Parameters#

The connection details for a volume group come as a separate step, not as part of creating it. Normally you would get the connection parameters the same way you get them for mounting to a VM, by pulling them up manually. The reason I wanted to write this up is that Terraform can get them the same way, it is just a query against the API instead of a click through the portal.

The endpoints come from a listConnectionParameters action on the volume group, and that is a POST, not a read. So it is not a data source. In azapi you reach it with azapi_resource_action:

resource "azapi_resource_action" "vg_connection_params" {
  for_each = local.volume_groups

  type        = "PureStorage.Block/storagePools/volumeGroups@${local.api_version}"
  resource_id = azapi_resource.volume_group[each.key].id
  action      = "listConnectionParameters"
  method      = "POST"

  response_export_values = ["*"]
}

output "iscsi_connection_params" {
  value = {
    for k, v in azapi_resource_action.vg_connection_params :
    k => v.output.iscsi.endpoints
  }
}

That gives you the iSCSI endpoints per volume group, keyed by name:

iscsi_connection_params = {
  "aro-worker-1" = [
    {
      ip  = "10.x.x.x"
      iqn = "iqn.2021-09.com.purestorage:..."
    },
  ]
  ...
}

Because it is a Terraform output, you can feed it straight into a downstream module or a config generator instead of copying endpoints around by hand. That is the whole reason to do this in Terraform rather than the portal.

One behaviour to know about: azapi_resource_action runs on every apply by default. That is usually what you want here, since the endpoints should reflect current state, but it does mean the action always shows up as a change in your plan output. It is not drift.

Configuring the Nodes for iSCSI#

RHCOS workers do not come with iSCSI multipath configured, and that has to be in place before discovery below will behave correctly. It is delivered the same way any host-level config reaches CoreOS on OpenShift, an OpenShift MachineConfig that drops in multipath.conf and the matching udev rules, applied once at the cluster level rather than per node. The PX-CSI + ARO support KB has the exact MachineConfig for this, use it rather than hand-rolling your own multipath config.

Validating the iSCSI Connection on the Nodes#

Before handing anything to Portworx, I wanted to confirm the endpoints actually work from the node side. You can debug directly into a worker with oc:

oc debug node/<node-name> -T -- chroot /host

From inside that shell, run discovery against one of the endpoints the Terraform output gave you:

iscsiadm -m discovery -t st -p <endpoint-ip>

A working target list back means the node can see the volume group. This is worth doing once by hand even though PX-CSI ends up managing the actual sessions, because it isolates network and target problems from anything Portworx-specific. If discovery fails here, nothing above it is going to work either.

Attaching Storage to Pods with PX-CSI#

The volume groups and endpoints above are the plumbing. Pods do not talk to any of that directly, they go through a StorageClass backed by the Portworx CSI driver:

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: everpure-block
provisioner: pxd.portworx.com
parameters:
  backend: pure_block
  csi.storage.k8s.io/fstype: xfs
allowVolumeExpansion: true

And a PVC against it:

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: everpure-test-pvc
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: everpure-block
  resources:
    requests:
      storage: 100Gi

That 100Gi is not an arbitrary round number, it is the size I have been testing with on this cluster. Note there is no Volume resource anywhere in the Terraform above, and no volume created ahead of time. PX-CSI provisions it dynamically off the volume group the moment this PVC is applied, sized to whatever the claim asks for.

This assumes the Portworx operator and a StorageCluster are already deployed on ARO, which is a one-time, cluster-level setup rather than something this Terraform touches. Two things caught me out doing that the first time: the operator is installed from Ecosystem → Software Catalog, not from Operators → OperatorHub the way you would expect on a normal OpenShift cluster, and the StorageCluster has to be created last, after everything else (namespace, monitoring, multipath config) is in place. Create it too early and you will be redoing it.

Deploying the Configuration#

terraform init -upgrade
terraform plan
terraform apply

The -upgrade matters if you are adding azapi to a workspace that only had azurerm before, otherwise init will not pick up the new provider.

The volume groups come up in well under a minute. To pull the connection parameters back out later without a full apply:

terraform output iscsi_connection_params

Things Worth Knowing#

Pin the API version. Already said it above, but it is the thing most likely to break this configuration six months from now.

Still one volume group per node, just not every node. My cluster has nine workers, but only three run the workload that needs storage, so I only created three volume groups, one per node in that set. Size the toset in volume_group.tf to the workers that actually need storage, not to worker_node_count.

I never set bandwidth or IOPS limits, and that was fine. The volume group API takes both, but I left them at the defaults. Given the worker network ceiling below, there was no point capping storage throughput below what the VM’s network could ever push anyway.

Watch the worker network ceiling. This came up when deploying the cluster and it is worth repeating here, because it is the thing that surprised me. The default ARO worker sizes are small, and the bandwidth cap on the VM will bite before the storage does. If you are sizing for throughput, start with the VM network limits and work backwards, and do not bother tuning volume group limits until you have.
