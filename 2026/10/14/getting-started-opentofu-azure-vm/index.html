Getting Started with OpenTofu by Deploying an Azure VM

October 14, 2026 · 5 min read · 969 words
Share

Are you looking at OpenTofu and wondering how much work it is to switch from Terraform? OpenTofu came up recently in a conversation about deployment and automation, and rather than guess, I installed it and tried it against my own lab. It turned out to be a very small change.

Introduction#

OpenTofu is the open source fork of Terraform. It was created in 2023 when HashiCorp moved Terraform to the Business Source License, and it is now a Linux Foundation project under the MPL 2.0 license.

It uses the same HCL, the same providers and the same state format. The biggest difference day to day is the command, which is tofu instead of terraform.

In this post I will install OpenTofu, point it at an existing Terraform project to see what breaks, and then deploy a simple Azure VM from scratch.

Pre-Requisites#

  • Homebrew or another way to install OpenTofu
  • Azure CLI logged in with az login
  • An Azure subscription you can create resources in
  • An SSH key pair

Install OpenTofu#

On macOS this is one command.

brew install opentofu
tofu version

At the time of writing this installed OpenTofu v1.13.1.

Testing an Existing Terraform Project#

Before writing anything new, I wanted to know if my existing projects would just work. I picked one of my Azure lab projects that keeps its state in HCP Terraform and ran tofu init against it.

The first attempt failed.

Error: Hostname is required for the cloud backend

OpenTofu does not provide a default "hostname" attribute, so it must be set
to the hostname of the cloud backend.

Terraform assumes app.terraform.io when the cloud block does not specify a host. OpenTofu does not, so you need to add it. Terraform is fine with the extra line, so the same file works with both.

terraform {
  cloud {
    hostname     = "app.terraform.io"
    organization = "my-org"
    workspaces {
      name = "my-workspace"
    }
  }
}

After that tofu init worked and picked up my existing HCP Terraform login. It also printed a warning about the lock file.

OpenTofu automatically rewrote some entries in your dependency lock file:
  - registry.terraform.io/hashicorp/azurerm => registry.opentofu.org/hashicorp/azurerm

OpenTofu pulls providers from its own registry, and those builds are not byte for byte identical to the HashiCorp ones, so the hashes change. If you need to share a repository between both tools, expect some noise in .terraform.lock.hcl.

A tofu plan then refreshed every resource and produced a normal diff. For an existing project that was the whole migration.

Deploying an Azure VM from Scratch#

Next I wanted to build something new with OpenTofu from the start. The goal was a simple deployment of a resource group, VNet, subnet, NSG, public IP and an Ubuntu VM.

The complete code is available as a zip , with a terraform.auto.tfvars.example to copy and fill in.

State#

I used local state for this one. A remote backend like an Azure Storage Account needs to exist before you can use it, which turns a quick test into a bootstrap project. If you want to move it later, swap the backend and run tofu init -migrate-state.

terraform {
  backend "local" {}
}

Providers#

This looks exactly like it would for Terraform. OpenTofu reads hashicorp/azurerm and resolves it from the OpenTofu registry.

terraform {
  required_version = ">= 1.8"

  required_providers {
    azurerm = {
      source = "hashicorp/azurerm"
    }
  }
}

provider "azurerm" {
  features {}
  subscription_id = var.subscription_id
}

Network#

There is no Bastion in a brand new VNet, so the VM gets a public IP. The NSG only allows SSH from a single CIDR, which you set to your own public IP.

resource "azurerm_network_security_group" "vm" {
  name                = "${var.vm_name}-nsg"
  resource_group_name = azurerm_resource_group.rg.name
  location            = azurerm_resource_group.rg.location

  security_rule {
    name                       = "SSH-Admin"
    priority                   = 100
    direction                  = "Inbound"
    access                     = "Allow"
    protocol                   = "Tcp"
    source_port_range          = "*"
    destination_port_range     = "22"
    source_address_prefix      = var.ssh_source_cidr
    destination_address_prefix = "*"
  }
}

The VNet, subnet, NSG association and public IP are in network.tf in the zip.

Virtual Machine#

The VM is a Standard_B2s running Ubuntu 24.04 LTS with SSH key authentication only.

resource "azurerm_linux_virtual_machine" "vm" {
  name                            = var.vm_name
  resource_group_name             = azurerm_resource_group.rg.name
  location                        = azurerm_resource_group.rg.location
  size                            = var.vm_size
  admin_username                  = var.admin_username
  network_interface_ids           = [azurerm_network_interface.vm.id]
  disable_password_authentication = true

  admin_ssh_key {
    username   = var.admin_username
    public_key = file(pathexpand(var.ssh_public_key_path))
  }

  os_disk {
    caching              = "ReadWrite"
    storage_account_type = "StandardSSD_LRS"
  }

  source_image_reference {
    publisher = "Canonical"
    offer     = "ubuntu-24_04-lts"
    sku       = "server"
    version   = "latest"
  }
}

Note: Check that your VM size is available in the region and zone you pick. Standard_B2s was restricted in two of the three westus2 zones on my subscription, so I left the VM regional instead of pinning a zone. az vm list-skus -l westus2 --size Standard_B2s will show any restrictions.

Deploy#

Copy the example variables file and fill in your subscription ID and public IP.

cp terraform.auto.tfvars.example terraform.auto.tfvars

Then run the same workflow you would with Terraform.

tofu init
tofu plan -out=tfplan
tofu apply tfplan

The plan showed 8 resources to add, and the apply finished in about a minute.

Apply complete! Resources: 8 added, 0 changed, 0 destroyed.

Outputs:

public_ip = "203.0.113.25"
ssh_command = "ssh azureuser@203.0.113.25"

Running tofu plan one more time came back with “No changes. Your infrastructure matches the configuration.” The state and Azure agree.

When you are done, tofu destroy removes everything.

Conclusion#

For my existing projects, switching to OpenTofu was one line in the cloud block and a refreshed lock file. For new projects there is nothing to learn beyond typing tofu instead of terraform. In a future post I will look at some of the features OpenTofu has added since the fork, like state encryption.

If you have questions or feedback, feel free to leave a comment below!
