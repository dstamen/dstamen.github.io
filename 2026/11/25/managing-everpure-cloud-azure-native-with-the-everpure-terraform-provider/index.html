Managing Everpure Cloud Azure Native with the Everpure Terraform Provider

November 25, 2026 · 13 min read · 2681 words
Share

Are you managing Everpure Cloud Azure Native with azapi today and pinning api-versions to keep the plan from blowing up? The Everpure Azure provider is now on the Terraform Registry, and it replaces all of that with real resources. I have been testing it in my lab since the early builds, and with 1.0.0 out I rebuilt everything from scratch to see how it holds up.

Why a Provider#

In my first Terraform post everything went through azapi_resource against the PureStorage.Block API. It works, but you carry a lot yourself. Every resource is pinned to the api-version that created it, because the resource provider rejects a PUT on an existing resource after a version change. Mounting a volume means calling listConnectionParameters, pulling the controller IPs and IQNs out by index, picking MountIscsiLinux or MountIscsiWindows and building the extension settings by hand.

The provider turns that into typed resources with plan-time validation, sane defaults and one resource for the VM connection. It authenticates the same way azurerm and azapi do, so az login is enough to get started.

Prerequisites#

  • An active Everpure Cloud Reservation in the region you are deploying to
  • The PureStorage.Block resource provider registered
  • A subnet delegated to PureStorage.Block/storagePools
  • A subnet for the VMs that can reach the pool subnet
  • Terraform 1.16 or newer, for the console SSH user action
  • The Azure CLI , logged in with az login
az provider register --namespace PureStorage.Block

The complete code is available as a zip , with a terraform.auto.tfvars.example to copy and fill in. It deploys the pool, a Linux and a Windows VM, and a volume group and volume for each one.

Configuring the Provider#

The local name has to be everpure, because every resource type starts with everpure_. The “Use provider” snippet on the registry page shows a different local name, so change it.

terraform {
  required_version = ">= 1.16"

  required_providers {
    everpure = {
      source  = "PureStorage-OpenConnect/everpure-azure"
      version = "1.0.0"
    }
    azurerm = {
      source  = "hashicorp/azurerm"
      version = ">= 4.0"
    }
    random = {
      source = "hashicorp/random"
    }
  }
}

provider "everpure" {
  subscription_id = var.subscription_id
}

provider "azurerm" {
  features {}
  subscription_id = var.subscription_id
}

Nothing else is needed in the provider block. With no credentials configured it uses whatever az login last authenticated as, and it picks up the same ARM_* environment variables as azurerm in CI. random is only there for the Windows VM’s admin password.

Looking Up the Reservation#

The reservation comes from the Azure Marketplace, so I read it with a data source instead of managing it. The pool needs the full resource ID, and this way you only have to know the name and resource group:

data "everpure_azure_reservation" "lab" {
  name                = var.reservation_name
  resource_group_name = var.reservation_resource_group
}

A nice side effect is that a typo in the name fails at plan time, not 30 minutes into a pool create.

Provisioning the Storage Pool#

The pool takes the reservation, the zone, bandwidth and the delegated subnet. Bandwidth has to be at least 800 MB/s and can be changed later in place. The zone and subnet can’t, changing either one replaces the pool.

resource "everpure_azure_storage_pool" "pool" {
  name                          = var.pool_name
  resource_group_name           = var.resource_group
  location                      = var.location
  zone                          = var.zone
  reservation_id                = data.everpure_azure_reservation.lab.id
  provisioned_bandwidth_in_mbps = var.bandwidth
  tags                          = var.tags

  vnet_injection {
    subnet_id = var.subnet_id
  }

  dynamic "platform_console" {
    for_each = var.platform_console_enabled ? [1] : []
    content {
      gui_enabled = var.platform_console_gui_api_enabled
      api_enabled = var.platform_console_gui_api_enabled
      cli_enabled = var.platform_console_cli_enabled
    }
  }

  lifecycle {
    action_trigger {
      events    = [after_create]
      condition = var.platform_console_enabled && var.console_ssh_username != null
      actions   = [action.everpure_azure_create_platform_console_ssh_user.console]
    }
  }
}

The platform_console block turns on GUI, REST API and SSH access to the console from the pool’s subnet. Leave it out and the console stays off. When it is there, at least one of the three has to be true, and gui_enabled and api_enabled have to match, so I drive both from one variable. The action_trigger creates a console SSH user right after the pool, I cover that in the console section below.

Pool creation is the slow part. Mine took about 30 minutes, and terraform apply just waits for it.

Creating the Volume Group and Volume#

The volume group is where performance limits and snapshot schedules live. I gave each VM its own volume group, so the Windows and Linux hosts never share a LUN.

resource "everpure_azure_volume_group" "vg" {
  for_each        = local.vms
  name            = each.value.name
  storage_pool_id = everpure_azure_storage_pool.pool.id
  iops_limit      = var.vg_iops_limit

  deletion_protection  = !var.allow_destroy
  eradicate_on_destroy = var.allow_destroy
}

resource "everpure_azure_volume" "vol" {
  for_each                = local.vms
  name                    = "data1"
  volume_group_id         = everpure_azure_volume_group.vg[each.key].id
  provisioned_size_in_gib = var.vol_size_gib

  deletion_protection  = !var.allow_destroy
  eradicate_on_destroy = var.allow_destroy
}

Sizes can be set in GiB now instead of bytes. Volumes can grow in place but not shrink. I will get to allow_destroy in the teardown section.

Mounting the Volume to a VM#

This is the part I like the most. One resource connects the VM to one or more volume groups. The provider looks up the iSCSI endpoints itself and installs the Linux or Windows extension to match the VM’s OS.

resource "everpure_azure_virtual_machine_connection" "vm" {
  for_each            = local.vms
  virtual_machine_id  = local.vm_ids[each.key]
  volume_group_ids    = [everpure_azure_volume_group.vg[each.key].id]
  iscsi_session_count = var.iscsi_sessions

  # Windows only, the first MPIO setup needs a reboot to finish
  reboot_allowed = each.value.os == "windows"

  depends_on = [everpure_azure_volume.vol]
}

Keep that depends_on. The connection only references the volume group, so without it Terraform can connect an empty group, which fails. The same goes for volumes you add later. A volume created after the connection is not visible on the VM until you rescan:

sudo iscsiadm -m session --rescan

On Windows set reboot_allowed = true, otherwise the first apply finishes with a warning telling you to reboot before MPIO is done.

Deploying#

Copy the example variables, fill in your values and run the usual workflow:

cp terraform.auto.tfvars.example terraform.auto.tfvars
terraform init
terraform plan -out=tfplan
terraform apply tfplan

The plan comes out to 12 resources: the pool, two VMs and their NICs, a volume group, volume and connection per VM, and the Windows password. Everything after the pool took about three more minutes, the volume groups and volumes under a minute each and the two VM connections about a minute.

Platform Console Access#

There are two ways into the console with this provider, and both are in console.tf in the zip.

An SSH User#

The everpure_azure_create_platform_console_ssh_user action creates a console user with your SSH public key. Actions only run when something triggers them, and here the pool’s action_trigger runs it once, right after the pool is created. caller.id is the pool that triggered it, which is why this needs Terraform 1.16:

action "everpure_azure_create_platform_console_ssh_user" "console" {
  config {
    storage_pool_id = caller.id
    username        = var.console_ssh_username
    role            = var.console_ssh_role
    public_key      = file(pathexpand(var.ssh_public_key_path))
  }
}

It only runs on create. Changing the key or role later does nothing, and running it again for the same user fails with a 409. You can also run it on demand:

terraform apply -invoke=action.everpure_azure_create_platform_console_ssh_user.console

The console is only reachable from inside the VNet. I don’t have a public IP on anything, so I go through Azure Bastion to the Linux VM with agent forwarding, then on to the management IP from the console output. The private key never leaves my laptop:

az network bastion ssh -g <bastion-rg> -n <bastion-name> \
  --target-resource-id <linux-vm-id> \
  --auth-type ssh-key --username azureuser --ssh-key ~/.ssh/id_rsa -- -A

ssh everpure-ssh@<management-ip> purearray list

Name                                     ID                                    OS          Version
sp-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx  xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx  Purity//FA  6.12.1.post4

Temporary Credentials#

The everpure_azure_platform_console_activation_credentials ephemeral resource gets a temporary password for the default console user, good for about four hours. Every request issues a new password and invalidates the previous one, so I put it behind a variable that is off by default. Normal plans never touch it:

ephemeral "everpure_azure_platform_console_activation_credentials" "this" {
  count           = var.console_credentials ? 1 : 0
  storage_pool_id = everpure_azure_storage_pool.pool.id
}

resource "terraform_data" "console_creds" {
  count            = var.console_credentials ? 1 : 0
  triggers_replace = plantimestamp()

  provisioner "local-exec" {
    command = "umask 077 && printf 'username=%s\\npassword=%s\\nexpires_at=%s\\n' \"$U\" \"$P\" \"$E\" > .console-creds"
    environment = {
      U = ephemeral.everpure_azure_platform_console_activation_credentials.this[0].username
      P = ephemeral.everpure_azure_platform_console_activation_credentials.this[0].password
      E = ephemeral.everpure_azure_platform_console_activation_credentials.this[0].expires_at
    }
  }
}

When you need a login:

terraform apply -var console_credentials=true
cat .console-creds

The password never goes into state, and Terraform hides the provisioner output on its own because of the ephemeral value.

Importing Existing Resources#

Most of us already have pools that were created in the portal or with azapi. Those can be brought under Terraform with an import block. The pool, volume groups and volumes can be imported by identity, which needs Terraform 1.12 or newer, or by the full resource id. I tested it on an existing pool in my lab that had never been managed by this provider.

You don’t have to write the resource block yourself. Start with just the import block, in a new root or next to your existing config:

import {
  to = everpure_azure_storage_pool.pool
  identity = {
    subscription_id     = "00000000-0000-0000-0000-000000000000"
    resource_group_name = "rg-storage"
    name                = "existing-pool"
  }
}

Then have the plan write the config for you:

terraform plan -generate-config-out=pool.tf

Plan: 1 to import, 0 to add, 0 to change, 0 to destroy.

The generated pool.tf is close, but there is one line to fix. It includes provider = everpure-azure, and because the local name is everpure, Terraform reads that as a separate provider called hashicorp/everpure-azure. The next plan fails with “Inconsistent dependency lock file”. Delete that line. After cleanup it looks like this:

resource "everpure_azure_storage_pool" "pool" {
  location                      = "westus2"
  name                          = "existing-pool"
  provisioned_bandwidth_in_mbps = 2048
  reservation_id                = "/subscriptions/.../reservations/my-reservation"
  resource_group_name           = "rg-storage"
  zone                          = "1"

  platform_console {
    api_enabled = true
    cli_enabled = true
    gui_enabled = true
  }

  vnet_injection {
    subnet_id = "/subscriptions/.../subnets/pool-subnet"
  }

  lifecycle {
    prevent_destroy = true
  }
}

I added the prevent_destroy myself. This is a shared pool, and I didn’t want one stray terraform destroy taking it out. Before you apply, make sure the plan shows 0 to change. Anything Terraform wants to change during an import gets applied to the real pool.

terraform plan -out=tfplan
terraform apply tfplan

everpure_azure_storage_pool.pool: Importing... [identity=name=existing-pool,resource_group_name=rg-storage,...]
everpure_azure_storage_pool.pool: Import complete

Apply complete! Resources: 1 imported, 0 added, 0 changed, 0 destroyed.

The plan right after came back with no changes, and terraform plan -destroy stops with “Instance cannot be destroyed”, which is exactly what you want for a pool other people are using.

If you prefer the older way, the provider docs also show terraform import with the full resource ID:

terraform import everpure_azure_storage_pool.pool \
  "/subscriptions/<sub>/resourceGroups/rg-storage/providers/PureStorage.Block/storagePools/existing-pool"

Volume Groups and Volumes#

Volume groups and volumes import the same way. Their identity adds storage_pool_name, and for volumes volume_group_name. I imported a volume group with four volumes in it, all in the same plan, with one import block each:

import {
  to = everpure_azure_volume_group.app
  identity = {
    subscription_id     = "00000000-0000-0000-0000-000000000000"
    resource_group_name = "rg-storage"
    storage_pool_name   = "existing-pool"
    name                = "app-vg"
  }
}

import {
  to = everpure_azure_volume.data
  identity = {
    subscription_id     = "00000000-0000-0000-0000-000000000000"
    resource_group_name = "rg-storage"
    storage_pool_name   = "existing-pool"
    volume_group_name   = "app-vg"
    name                = "data"
  }
}

-generate-config-out puts the same provider = everpure-azure line on every generated volume group and volume, so delete those too. It also hard codes the parent IDs. I swapped them for references so the volumes follow the volume group and the volume group follows the pool:

resource "everpure_azure_volume_group" "app" {
  name                 = "app-vg"
  storage_pool_id      = everpure_azure_storage_pool.pool.id
  source_type          = "none"
  deletion_protection  = true
  eradicate_on_destroy = false

  lifecycle {
    prevent_destroy = true
  }
}

resource "everpure_azure_volume" "data" {
  name                      = "data"
  volume_group_id           = everpure_azure_volume_group.app.id
  provisioned_size_in_bytes = 107374182400 # 100 GiB
  source_type               = "none"
  deletion_protection       = true
  eradicate_on_destroy      = false

  lifecycle {
    prevent_destroy = true
  }
}

The generated config uses provisioned_size_in_bytes, and I left it that way so the plan stayed at 0 to change.

Apply complete! Resources: 5 imported, 0 added, 0 changed, 0 destroyed.

Letting Go Without Deleting#

Since this was just a test against shared resources, I wanted Terraform to forget about them afterwards. Removing the resource blocks would make Terraform try to destroy them, so instead replace each one with a removed block and set destroy = false:

removed {
  from = everpure_azure_volume.data

  lifecycle {
    destroy = false
  }
}

The plan shows each resource “will no longer be managed by Terraform, but will not be destroyed”.

Plan: 0 to add, 0 to change, 0 to destroy.
Apply complete! Resources: 0 added, 0 changed, 0 destroyed.

The state was empty after that and the pool, volume group and volumes were all still there in the portal. terraform state rm does the same thing from the command line if you don’t want it in code.

Tearing It Down#

Volume groups and volumes default to deletion_protection = true, and a destroy soft-deletes them. A soft-deleted volume group or volume still blocks deleting the pool. That is the right default, but for a lab I wrap both flags in one allow_destroy variable, as you saw above.

A plain terraform destroy with protection on fails at plan time with a clear message, so nothing gets half torn down. To remove everything, turn protection off first, then destroy with the same variable:

terraform apply -var allow_destroy=true
terraform destroy -var allow_destroy=true

The first apply only changes state, so it takes seconds. The destroy takes about 20 minutes, most of it the pool.

There are two catches I ran into with 1.0.0 and Terraform 1.17.

The first is the action_trigger. terraform destroy fails at plan time with “Reference to uninitialized variable” on the trigger’s condition, before anything is deleted. Taking out just the lifecycle block then fails on caller.id in the action, so for the destroy I comment out both the lifecycle block in pool.tf and the action block in console.tf, then put them back after. The SSH user was created on day one, so nothing is lost.

The second is Windows. If the disk has been brought online and used, removing the VM connection fails because the extension can’t log out an iSCSI session that has a disk in use. Take the Pure disks offline before you destroy:

Get-Disk | Where FriendlyName -like 'PURE*' | Set-Disk -IsOffline $true

If you already hit the error, offlining afterwards didn’t help in my lab, the retry came back with the same failure. Since the VM is being destroyed anyway I removed the connection from state and ran the destroy again:

terraform state rm 'everpure_azure_virtual_machine_connection.vm["win"]'
terraform destroy -var allow_destroy=true

Things Worth Knowing#

The local name must be everpure. The registry snippet uses a different one.

Fix the generated provider line on import. -generate-config-out writes provider = everpure-azure. Delete it.

Rescan after adding volumes. The VM connection doesn’t rescan for you when a group it is already connected to gets a new volume.

Keep console credentials gated. Every plan and apply opens the ephemeral resource, so a single terraform apply would issue two passwords and only the second one works.

Snapshots are in there too. The zip has a snapshot file with a manual snapshot, a volume restored from it and a volume group cloned from it. Terraform ignores it until you rename it to snapshot.tf. I will dig into snapshots and restores with the provider in a future post.
