Which of Your Azure Resources Are Zone Resilient

November 21, 2026 · 6 min read · 1140 words
Share

Part of the series: Azure Infrastructure Resiliency

Are you wondering which of your Azure resources are zone resilient and which are not? The Resources view in Azure Infrastructure Resiliency Manager answers that for everything in your scope.

This is the next part of the Azure Infrastructure Resiliency series. In part 1 I walked through all the components of Infrastructure Resiliency, and now I want to go deep on the first one, Resources.

Where to Find It#

Open Resiliency in the Azure portal and select Overview. The Resource resiliency tab gives you the summary for every resource in your scope.

For the full list, expand Infrastructure resiliency in the left menu and select Resources.

At the top you get a total with a split between zonal resilient and non-zonal resilient resources. Below that is the list, with the name, type, a Resilient or Non-resilient status, subscription, resource group and a link to the recommendations for each resource.

You can filter by subscription, resource group, resource type, location and tags.

The Three States#

Every resource lands in one of three states.

  • Zone resilient, which means the service detected a zone resilience solution
  • Non zone resilient, which means it did not find one
  • Not evaluated, which means the resource type is not supported or you excluded it

My subscription showed 184 resources, 13 zone resilient and 171 not.

That count covers every supported resource type and not just VMs, so VMs are only part of it. Some types, like network interfaces and NSGs, are left out of discovery completely and never show up in the count.

What Counts as Zone Resilient#

The service does not guess. It only recognizes specific solutions for each resource type, and Microsoft publishes the list in the support matrix .

Most entries are what you would expect. A storage account on ZRS, a zone redundant load balancer, a Standard SKU public IP, a zone redundant managed disk and so on.

Virtual Machines#

Virtual machines are the interesting one, because there are three ways to be detected.

SolutionWhat it means
VM in Multi-Zone VMSSThe VM is an instance of a scale set that spans zones
VM with cross-zone recoveryThe VM is replicated to another zone, for example with Azure Site Recovery
Zone-pinned VM with ZRS data disksThe VM is pinned to one zone and its data disks are zone redundant

If a VM does not match one of those three, it shows up as non zone resilient. In my subscription that was most of them. About half had no zone at all, and every one that was zonal was in zone 1 with LRS disks.

Checking It from the CLI#

You can check the same inputs yourself without opening the portal. Azure Resource Graph is the easiest way, since the VM, scale set and disk details all live in different places and it can join them in one query. If you have not used it before, add the extension first.

az extension add --name resource-graph

This query lists every VM with its zone, whether it is an instance of a multi-zone scale set, and whether all of its data disks are ZRS. Add --subscriptions <subscription id> to scope it to one subscription.

az graph query --first 1000 -q "
Resources
| where type =~ 'microsoft.compute/virtualmachines'
| extend vmId = tolower(id), zone = tostring(zones[0]), vmssId = tolower(tostring(properties.virtualMachineScaleSet.id))
| join kind=leftouter (
    Resources
    | where type =~ 'microsoft.compute/virtualmachinescalesets'
    | project vmssId = tolower(id), vmssZones = array_length(zones)
  ) on vmssId
| join kind=leftouter (
    Resources
    | where type =~ 'microsoft.compute/disks' and isempty(properties.osType)
    | summarize dataDisks = count(), zrsDisks = countif(tostring(sku.name) endswith 'ZRS') by vmId = tolower(tostring(managedBy))
  ) on vmId
| project name, resourceGroup, zone, inMultiZoneVmss = (vmssZones > 1), zrsDataDisks = (dataDisks > 0 and dataDisks == zrsDisks)
| order by name asc" --query "data[]" -o table

A blank zone means the VM is regional and has no zone at all. A VM is a match for the first solution when inMultiZoneVmss is true, and for the third when it has a zone and zrsDataDisks is true. The query filters out the OS disk because the support matrix only looks at data disks.

The second solution, cross-zone recovery, lives in the Recovery Services vault. This lists the VMs that are replicated with Azure Site Recovery and the zone they replicate to.

az graph query -q "
RecoveryServicesResources
| where type =~ 'microsoft.recoveryservices/vaults/replicationfabrics/replicationprotectioncontainers/replicationprotecteditems'
| project vm = properties.friendlyName, targetZone = properties.providerSpecificDetails.recoveryAvailabilityZone" --query "data[]" -o table

I do not have any Site Recovery replicated items in my subscription, so I could not test that last one. Treat it as a starting point.

None of my VMs matched on the first query. Nothing was in a multi-zone scale set and none had ZRS data disks. The portal disagreed on two of them.

Two VMs That Showed Up as Resilient#

Two of my VMs were marked zone resilient even though the query above says they should not be. Both are pinned to zone 1, and every disk on them is LRS.

What they have in common is that they are instances of a Flexible scale set. That scale set is set to zone 1 only, so it is not multi-zone.

My guess was that the service sees the scale set and counts the VM as resilient without checking which zones the scale set covers. To test it I deployed two throwaway Flexible scale sets with LRS disks, one set to zone 1 only and one spread across zones 1, 2 and 3. Then I added both to a service group with the zonal resiliency goal. Service groups get their own post, but this is the view that shows the detected solution for each resource.

Both scale sets got the same result. Every instance, including the ones in the zone 1 only scale set, shows VM in Multi-Zone VMSS as the solution configured. The zone 1 only scale set itself still shows Not configured, so you can end up with a resilient VM inside a scale set that is not.

So the service counts a VM as resilient because it is in a scale set, and at least for Flexible scale sets it does not look at which zones the scale set covers. A VM that only lives in zone 1 can still show up with a green mark.

If you manage a scale set, do not take that mark at face value. Check the zones on the scale set yourself.
