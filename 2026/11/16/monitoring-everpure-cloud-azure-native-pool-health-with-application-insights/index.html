Monitoring Everpure Cloud Azure Native Pool Health with Application Insights

November 16, 2026 · 7 min read · 1437 words
Share

Are you looking for a way to trend capacity and performance for an Everpure Cloud Azure Native storage pool inside Azure? The pool exposes a getHealthStatus action through ARM that returns bandwidth, IOPS, space and data reduction, but it only gives you a point in time. I wanted history and a dashboard, so I built a small Azure Function that calls it every minute and pushes the results into Application Insights as custom metrics.

Everything here uses the getHealthStatus API, and the Function and dashboards are a reference example, so use them as a starting point for your own version.

How It Works#

  • A Python Azure Function on a timer trigger, running on the Consumption plan
  • The Function’s managed identity gets a custom role scoped to just the storage pool
  • Each run pushes pool metrics, then walks every volume group and volume in the pool and pushes per-volume space metrics
  • Application Insights is workspace-based, so the same data lands in a Log Analytics workspace you can query from a Workbook or from Grafana

Prerequisites#

  • An existing Everpure Cloud Azure Native storage pool (PureStorage.Block/storagePools)
  • The Azure CLI , logged in with rights to create resources and role assignments
  • Azure Functions Core Tools v4 to publish the Function
  • Python 3.12 if you want to run the Function locally

Provisioning the Infrastructure#

Each pool gets its own Log Analytics workspace, Application Insights resource, storage account and Function App. That keeps the queries simple since there’s nothing to filter by pool.

RG=<rg>; POOL=<pool>; LOC=westus2

az monitor log-analytics workspace create -g $RG -n log-$POOL-health -l $LOC
WS_ID=$(az monitor log-analytics workspace show -g $RG -n log-$POOL-health --query id -o tsv)

az monitor app-insights component create -g $RG -a appi-$POOL-health -l $LOC --workspace "$WS_ID"

az storage account create -g $RG -n st${POOL//-/}health -l $LOC --sku Standard_LRS \
  --https-only true --min-tls-version TLS1_2

az functionapp create -g $RG -n func-$POOL-health \
  --storage-account st${POOL//-/}health \
  --consumption-plan-location $LOC \
  --runtime python --runtime-version 3.12 --functions-version 4 --os-type Linux \
  --app-insights appi-$POOL-health

az functionapp config appsettings set -g $RG -n func-$POOL-health --settings \
  SUB=<subscription-id> RG=$RG POOL=$POOL API_VERSION=2026-05-01-preview

The --https-only true isn’t optional in my subscription. There’s an Azure Policy that denies storage accounts unless supportsHttpsTrafficOnly is set explicitly on the request, so you get RequestDisallowedByPolicy without it.

The Custom Role#

Reader on the pool isn’t enough. getHealthStatus is an /action operation, and Reader’s */read wildcard doesn’t cover actions, even ones that only read. So the Function gets a small custom role with read plus that one action, assigned at the pool scope.

{
  "Name": "PureStorage Block Pool Health Reader",
  "Description": "Read access plus the PureStorage.Block storagePools getHealthStatus action.",
  "Actions": [
    "*/read",
    "PureStorage.Block/storagePools/getHealthStatus/action"
  ],
  "NotActions": [],
  "AssignableScopes": ["/subscriptions/<subscription-id>"]
}

Create it once per subscription, then turn on the Function App’s managed identity and assign the role on the pool.

az role definition create --role-definition pool-health-role.json

PRINCIPAL_ID=$(az functionapp identity assign -g <rg> -n func-<pool>-health --query principalId -o tsv)
POOL_ID=$(az resource show -g <rg> -n <pool> --resource-type PureStorage.Block/storagePools --query id -o tsv)

az role assignment create --assignee "$PRINCIPAL_ID" \
  --role "PureStorage Block Pool Health Reader" --scope "$POOL_ID"

If the assignment fails with “Cannot find user or service principal in graph database” right after assigning the identity, just wait and retry. The service principal takes 10 to 60 seconds to show up.

The Function#

The Function gets a token from its managed identity, calls getHealthStatus, converts bytes to MiB and GiB and sends each value to Application Insights. I post straight to the ingestion endpoint from the connection string instead of pulling in the full OpenTelemetry SDK, it’s one small JSON envelope per metric.

@app.timer_trigger(schedule="0 * * * * *", arg_name="mytimer", run_on_startup=False)
def poll_pool_health(mytimer: func.TimerRequest) -> None:
    try:
        token = credential.get_token("https://management.azure.com/.default").token
        url = (
            f"https://management.azure.com/subscriptions/{SUB}/resourceGroups/{RG}"
            f"/providers/PureStorage.Block/storagePools/{POOL}/getHealthStatus"
            f"?api-version={API_VERSION}"
        )
        resp = requests.post(url, headers={"Authorization": f"Bearer {token}"}, timeout=30)
        if not resp.ok:
            logging.error("getHealthStatus call failed: %s %s", resp.status_code, resp.text)
        resp.raise_for_status()
        health = resp.json()["health"]
    except Exception:
        logging.exception("poll_pool_health failed")
        raise

    props = {"pool": POOL, "resourceGroup": RG, "subscriptionId": SUB}
    bw, iops, space = health["bandwidthUsage"], health["iopsUsage"], health["space"]

    track_metric("PoolBandwidthCurrentMiBps", bw["current"] / MIB, props)
    track_metric("PoolBandwidthProvisionedMiBps", bw["provisioned"] / MIB, props)
    track_metric("PoolBandwidthMaxMiBps", bw["max"] / MIB, props)
    track_metric("PoolIopsCurrent", iops["current"], props)
    track_metric("PoolIopsProvisioned", iops["provisioned"], props)
    track_metric("PoolIopsMax", iops["max"], props)
    track_metric("PoolSpaceTotalUsedGiB", space["totalUsed"] / GIB, props)
    track_metric("PoolSpaceUniqueGiB", space["unique"] / GIB, props)
    track_metric("PoolSpaceSnapshotsGiB", space["snapshots"] / GIB, props)
    track_metric("PoolSpaceSharedGiB", space["shared"] / GIB, props)
    track_metric("PoolDataReductionRatio", health["dataReductionRatio"], props)
    track_metric("PoolUsedCapacityPercentage", health["usedCapacityPercentage"], props)

usedCapacityPercentage is already a percent, so it goes in as is. On a mostly empty pool it’s a tiny number like 0.0002, not 0.02.

track_metric builds the envelope and posts it to {IngestionEndpoint}/v2/track:

def track_metric(name: str, value: float, properties: dict) -> None:
    envelope = {
        "name": "Microsoft.ApplicationInsights.Metric",
        "time": datetime.datetime.utcnow().isoformat() + "Z",
        "iKey": IKEY,
        "data": {
            "baseType": "MetricData",
            "baseData": {
                "ver": 2,
                "metrics": [{"name": name, "value": value, "count": 1}],
                "properties": properties,
            },
        },
    }
    resp = requests.post(f"{INGESTION_ENDPOINT}/v2/track", json=envelope, timeout=10)
    if not resp.ok:
        logging.warning("track_metric(%s) failed: %s %s", name, resp.status_code, resp.text)

The try/except with logging.exception matters more than it looks. Without it a failed run just shows up as a generic “Executed … (Failed)” trace in Application Insights, and you never see the actual 403 or whatever broke.

After the pool metrics, the Function lists the volume groups in the pool and the volumes in each one, and pushes VolumeSpaceTotalUsedGiB, VolumeSpaceUniqueGiB, VolumeSpaceSnapshotsGiB, VolumeSpaceSharedGiB and VolumeProvisionedSizeGiB for each volume with volumeGroup and volume as dimensions. Those are plain GET calls, so the */read in the custom role already covers them. That part is best effort, if it fails it gets logged but the run doesn’t fail since the pool metrics already went out.

To deploy the code:

cd function/
func azure functionapp publish func-<pool>-health

Dashboard Option 1: Azure Workbook#

The Workbook is attached to the Application Insights resource and queries customMetrics. The top has Capacity and Performance summary cards showing the latest reading, then trend charts for space, bandwidth and IOPS, and a Volumes table with Volume Group and Volume filters.

This is from the pool under a sustained write test. You can see bandwidth climb to the 2,048 MiB/s provisioned limit and flatten out while capacity keeps growing.

A basic query looks like this:

customMetrics
| where name == "PoolBandwidthCurrentMiBps"
| summarize avg(value) by bin(timestamp, 1m)
| render timechart

Dashboard Option 2: Azure Managed Grafana#

I also wanted to see if Grafana would be less fiddly for formatting, so I built the same dashboard in Azure Managed Grafana querying the Log Analytics workspace behind Application Insights.

Once it’s built it’s a lot more flexible. There are real units for bytes, data rates and percent, comma grouping out of the box, and a responsive grid with no margin hacks. It came with its own set of gotchas though:

  • The Essential tier is deprecated for new workspaces, so you are on the billed Standard tier. Check the pricing before you go this route for one pool.
  • Querying through the workspace instead of the Application Insights resource means the table is AppMetrics, not customMetrics, with Name, Sum and TimeGenerated instead of name, value and timestamp.
  • Creating a service account token to script dashboard deploys has the same propagation delay as the managed identity. Expect to retry.
  • A timeseries panel with options.legend.displayMode set to "hidden" rendered completely blank in Grafana 12.4.8. No error, and the query inspector showed valid data. Setting it to "list" fixed it. If you get a blank timeseries panel, check that first.

The same query against the workspace:

AppMetrics
| where Name == "PoolSpaceTotalUsedGiB"
| order by TimeGenerated desc
| take 1
| project TimeGenerated, Sum

For the volume filters, the volumeGroup and volume variables go into the query as ${volumeGroup:singlequote} inside an in (...) clause. The singlequote format is what turns a multi-select variable into a KQL list. Volume names aren’t unique across volume groups either, my test pool had a data1 in two different groups, so anything that repeats per volume keys on volume group and volume together.

Cleaning Up#

Everything for one pool lives in the same resource group, so cleanup is deleting the Function App, its plan and storage account, the Application Insights resource, the Log Analytics workspace, the Workbook and the Grafana workspace if you created one. Then remove the role assignment on the pool and delete the custom role once nothing else is using it.
