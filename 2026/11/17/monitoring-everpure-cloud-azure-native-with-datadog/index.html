Monitoring Everpure Cloud Azure Native with Datadog

November 17, 2026 · 6 min read · 1095 words
Share

Are you looking for a way to get Everpure Cloud Azure Native performance, capacity and billing into Datadog? In my last post I used an Azure Function to push getHealthStatus into Application Insights. That works if your monitoring stack lives in Azure, but a lot of customers already run Datadog for everything else.

Now that the storage pool has a platform console, it exposes the same native Purity OpenMetrics endpoint a FlashArray does. I wanted to see if the existing Datadog integration would just work against it.

Short answer, it does!

I also wanted the Azure side (provisioned vs used IOPS and bandwidth, and what the reservation is billing you) on the same dashboard, so I wrote a small custom Agent check for the ARM actions.

Here is where it ended up, two pools under load on the the dashboard.

Everything here uses the Purity OpenMetrics endpoint, the ARM APIs, and the Agent configs. Checks and dashboards are a reference example, so use them as a starting point for your own.

How It Works#

  • The purefa check is the community Datadog Pure Storage FlashArray integration . It scrapes the Purity OpenMetrics endpoints on the platform console.
  • The everpure_arm check is a custom Agent check that calls the ARM POST actions with the VM’s managed identity.
  • Both tag everything with storage_pool:<name> so one dashboard can filter across pools.

The platform console management IP is private, so the Agent has to run on a VM inside the same VNet as the pool’s delegated subnet.

Pre-Requisites#

  • An Everpure Cloud Azure Native storage pool with the platform console enabled
  • A Linux VM in the pool’s VNet for the Datadog Agent
  • A Datadog API key, and an application key for Terraform
  • The Azure CLI and Terraform

The complete code is available here .

Create an API Token on the Pool#

The OpenMetrics endpoints take an API token issued to a local user. SSH to the platform console management IP and create a read-only user, then log in as that user and create its token.

pureadmin create --role readonly dd-metrics
pureadmin create --api-token

If you don’t have the management IP handy you can pull it from ARM.

az rest --method get \
  --url "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/PureStorage.Block/storagePools/<pool>?api-version=2026-05-01-preview" \
  --query "properties.platformConsoleSettings.subnets[0].managementIpAddress" -o tsv

Give the Agent VM Access to ARM#

Same as the Application Insights setup, Reader is not enough. getHealthStatus and getBillingStatus are /action operations and */read doesn’t cover them. I created a custom role with just the pool and reservation actions.

{
  "Name": "Everpure Cloud Metrics Reader",
  "IsCustom": true,
  "Actions": [
    "PureStorage.Block/storagePools/read",
    "PureStorage.Block/storagePools/getHealthStatus/action",
    "PureStorage.Block/reservations/read",
    "PureStorage.Block/reservations/getBillingStatus/action",
    "PureStorage.Block/reservations/getBillingReport/action",
    "PureStorage.Block/reservations/getResourceLimits/action"
  ],
  "NotActions": [],
  "AssignableScopes": ["/subscriptions/<subscription-id>"]
}

Next you will need to turn on the VM’s managed identity and assign the role on the resource groups that hold the pool and the reservation.

az vm identity assign -g <rg> -n <agent-vm>
az role definition create --role-definition azure/everpure-metrics-reader-role.json
PID=$(az vm show -g <rg> -n <agent-vm> --query identity.principalId -o tsv)

for rg in <pool-rg> <reservation-rg>; do
  az role assignment create --assignee-object-id $PID --assignee-principal-type ServicePrincipal \
    --role "Everpure Cloud Metrics Reader" --scope /subscriptions/<sub>/resourceGroups/$rg
done

If the assignment says the role doesn’t exist right after you create it, wait a minute and retry. It takes a bit to propagate.

Install the Agent and Checks#

Copy the folder to the Agent VM and create pools.csv from the example. It holds the API token so keep it secure.

name,mgmt_ip,api_token
<pool>,<mgmt-ip>,<token>

Then run the install script.

export DD_API_KEY=<api key>
export DD_SITE=datadoghq.com
export AZ_SUBSCRIPTION_ID=<sub>
export AZ_RESOURCE_GROUPS="<pool-rg>"
sudo -E ./install.sh pools.csv

install.sh installs the Datadog Agent and the datadog-purefa==1.3.0 integration, writes both check configs, restarts the Agent and runs each check once so you can see the metric counts.

Each pool gets 5 instances, one per metrics path. Here is what the volumes one looks like.

- openmetrics_endpoint: https://<mgmt-ip>/metrics/volumes?namespace=purefa
  min_collection_interval: 120
  tls_verify: false
  tls_ignore_warning: true
  rename_labels:
    host: fa_host
  headers:
    Authorization: Bearer <API_TOKEN>
  tags:
    - cloud_provider:azure
    - platform:everpure_cloud_azure_native
    - storage_pool:<pool>
  extra_metrics:
    - purefa_volume_group_performance_throughput_iops: volume_group.performance_throughput_iops
    - purefa_volume_group_performance_bandwidth_bytes: volume_group.performance_bandwidth_bytes
    - purefa_volume_group_performance_latency_usec: volume_group.performance_latency_usec
    - purefa_volume_group_qos_iops_limit: volume_group.qos_iops_limit

A few things in there are on purpose.

  • rename_labels moves the FA host label to fa_host. Otherwise it collides with the Datadog host tag.
  • extra_metrics adds the volume group metrics back. purefa 1.3.0 doesn’t map them, so they get dropped without it.
  • I originally tagged with env:azure and Datadog treats env as reserved, so it’s cloud_provider:azure instead.

To check it, run the checks by hand.

sudo -u dd-agent datadog-agent check purefa
sudo -u dd-agent datadog-agent check everpure_arm

The ARM Check#

The everpure_arm check lists the pools in the subscription, filters by resource group, then calls getHealthStatus on each one and getBillingStatus on its reservation.

Auth is a token from IMDS, so there are no secrets on the VM for the Azure side.

You get IOPS and bandwidth current vs provisioned vs max, space by type, data reduction, alerts, and from the reservation billed capacity, used capacity and performance overage. You can also run it standalone off your az login to test before you install anything.

python3 agent/checks.d/everpure_arm.py --subscription <sub>

The Dashboard#

The dashboard is in Terraform using datadog_dashboard_json. It also writes a dashboard.json if you would rather import it by hand.

cd terraform
export TF_VAR_datadog_api_key=<api key>
export TF_VAR_datadog_app_key=<app key>
terraform init
terraform apply

It’s split into sections:

  • Fleet with every pool the ARM check can see, including ones without a platform console
  • Overview with data reduction, utilization, read and write IOPS and latency
  • Performance trends and the top volumes by IOPS and bandwidth
  • Volumes with a per-volume table, per-volume charts and volume group IOPS against the QoS limit
  • Capacity by type
  • Azure ARM usage vs provisioned for IOPS and bandwidth
  • Billing from the reservation

The template variables are subscription, storage_pool, reservation and volume.

The screenshot at the top is the TV version. TV mode doesn’t scroll, it shrinks the whole page to fit the screen, so the full dashboard ends up as a small strip in the middle of a wall screen. The TV dashboard is a second dashboard in the same Terraform that reuses the same widgets in a 16:9 layout.

Wrapping Up#

If you need to delete the dashboard, you can by running terraform destroy, uninstall the Agent from the VM, remove the role assignments and delete the custom role once nothing else uses it.

Don’t forget to remove the read-only user and its token on the pool.
