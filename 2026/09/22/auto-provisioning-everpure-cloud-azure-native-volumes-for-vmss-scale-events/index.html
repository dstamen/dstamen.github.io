Auto-Provisioning Everpure Cloud Azure Native Volumes for VMSS Scale Events

September 22, 2026 · 16 min read · 3300 words
Share

Are you scaling a VMSS workload that needs its own dedicated block volume per instance, one that shows up when the instance does and disappears when it’s gone? I went looking for the obvious way to wire that up on Everpure Cloud Azure Native and ran into a design that doesn’t actually exist in Azure, then built the one that does.

Disclaimer: this is a proof of concept showing what’s possible on Everpure Cloud Azure Native, not an officially supported pattern. I built it and validated it end to end against a live pool, including a 10-instance concurrent scale test, so I know it works. The shared-secret auth, the naming scheme, error handling, all of it is lab-grade. Treat this as a working example to build your own version from, not something to drop straight into production.

The Problem#

In Provisioning Everpure Cloud Azure Native Resources with Terraform I walked through creating a single storage pool, volume group, volume, and mounting it to one VM. That’s fine for a fixed VM. A VMSS is different: instances come and go on their own schedule, and I wanted each one to get its own volume group and volume the moment it boots, and have that volume group cleaned up the moment the instance is gone. No standing pool of pre-created volumes, no manual step.

My first instinct was Event Grid. Azure has system topics for plenty of resource types, and VMSS instance lifecycle felt like exactly the kind of thing that would be covered. It isn’t, though, and that turned into the first real lesson of this project (full story below in Lessons Learned). Short version: there’s no Event Grid signal for a VMSS instance being created, and nothing GA for one being deleted either.

The Approach#

With nothing external around to tell it what just happened, each instance has to act on its own, in both directions. On boot, the instance is the one thing that already knows it just showed up, so it can call out and provision its own storage right there. On termination, Scheduled Events delivers a Terminate notification to the instance itself via the Instance Metadata Service, with a configurable grace period before Azure proceeds regardless. That’s the same mechanism behind VMSS terminate notifications , and unlike Lifecycle Hooks it’s GA and fires for scale-in generally, not just one code path.

So the shape becomes: boot triggers create, a Terminate event triggers cleanup, and an Azure Function in between does the actual work against the PureStorage.Block API.

IMDS is local to the instance, not a network hop. The Function is the one real remote call each direction. Teal is the boot/create path, orange is terminate/delete.

Prerequisites#

Same shared infrastructure as the single-VM post, plus a VMSS:

  • An existing storage pool (standing one up takes up to 90 minutes, so new VolumeGroups/Volumes get created per instance instead)
  • The VNet and subnet the pool is injected into (VMSS instances need to be on a subnet that can already reach it)
  • Terraform, with the azapi, azurerm, and random providers
  • The Azure CLI logged in, since the Function code itself is deployed separately from terraform apply via zip deploy

termination_notification is what makes the Terminate scheduled event show up at all; without it Azure just deletes the instance and there’s nothing to poll for. custom_data is the only thing per-instance about this scale set otherwise. The model itself is identical for every instance, since each one figures out who it is at boot rather than being told.

VMSS_ID is built as a plain string from variables rather than referencing azurerm_linux_virtual_machine_scale_set.lab.id directly. That attribute reference would create a real dependency cycle: the scale set’s custom_data already depends on this Function App’s hostname, and Azure resource IDs are deterministic from subscription/RG/name/type regardless of whether the resource exists yet, so there’s no reason to wire the second direction through Terraform’s graph at all.

The Function’s managed identity gets exactly two role assignments, each scoped to one resource rather than the resource group:

  role_definition_name = "Contributor"
  principal_id         = azurerm_linux_function_app.orchestrator.identity[0].principal_id
}

resource "azurerm_role_assignment" "orch_vmss" {
  scope                = azurerm_linux_virtual_machine_scale_set.lab.id

Identifying the Instance#

IMDS gives you everything needed to self-identify, including the instance’s own full ARM resource ID:

curl -s -H "Metadata:true" "http://169.254.169.254/metadata/instance?api-version=2021-02-01" \
  | python3 -c "import json,sys; print(json.load(sys.stdin)['compute']['resourceId'])"

/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachineScaleSets/gso-ds-vmss01/virtualMachines/3

That’s the exact path an ARM call needs to target this one instance, no separate lookup required.

The Boot Script#

#!/bin/bash
set -euo pipefail

apt-get update -y
apt-get install -y jq multipath-tools

IMDS="http://169.254.169.254/metadata"
FUNC_URL="${func_base_url}"
SECRET="${shared_secret}"

META=$(curl -s -H "Metadata:true" "$IMDS/instance?api-version=2021-02-01")
VMID=$(echo "$META" | jq -r '.compute.vmId')
RESOURCE_ID=$(echo "$META" | jq -r '.compute.resourceId')
INSTANCE_ID=$(basename "$RESOURCE_ID")
SELF_NAME=$(hostname)
echo "$VMID" > /var/log/ec-vmid

curl -s -X POST -H "x-shared-secret: $SECRET" \
  "$FUNC_URL/api/provision?vmId=$VMID&instanceId=$INSTANCE_ID" \
  > /var/log/ec-provision.json

That call is where it gets interesting: the vendor MountIscsiLinux extension only handles the iSCSI session, not the filesystem (more on that in Lessons Learned below). So the rest of the script does its own formatting and mounting, plus watches for termination, as a real systemd service instead of a nohup loop, since a background job that just needs to keep running reliably for the life of the instance is exactly what systemd is for:

cat > /usr/local/bin/ec-agent.sh << EOS
#!/bin/bash
IMDS="http://169.254.169.254/metadata"
FUNC_URL="$FUNC_URL"
SECRET="$SECRET"
VMID="$VMID"
SELF="$SELF_NAME"
MOUNTPOINT=/mnt/ecvol
mkdir -p "\$MOUNTPOINT"

while true; do
  if ! mountpoint -q "\$MOUNTPOINT"; then
    MPATH_DEV=\$(multipath -ll 2>/dev/null | awk '/PURE,FlashArray/{print \$1; exit}')
    if [ -n "\$MPATH_DEV" ]; then
      DEV="/dev/mapper/\$MPATH_DEV"
      blkid "\$DEV" >/dev/null 2>&1 || mkfs.ext4 -F "\$DEV"
      mount "\$DEV" "\$MOUNTPOINT"
    fi
  fi

  EVENTS=\$(curl -s -H "Metadata:true" "\$IMDS/scheduledevents?api-version=2020-07-01")
  EVENTIDS=\$(echo "\$EVENTS" | jq -r --arg self "\$SELF" \\
    '.Events[] | select(.EventType=="Terminate" and (.Resources | index(\$self) != null)) | .EventId')
  if [ -n "\$EVENTIDS" ]; then
    curl -s -X POST -H "x-shared-secret: \$SECRET" "\$FUNC_URL/api/deprovision?vmId=\$VMID" >> /var/log/ec-deprovision.json
    for EID in \$EVENTIDS; do
      curl -s -X POST -H "Metadata:true" -H "Content-Type: application/json" \\
        -d "{\\"StartRequests\\":[{\\"EventId\\":\\"\$EID\\"}]}" "\$IMDS/scheduledevents?api-version=2020-07-01" >/dev/null
    done
    exit 0
  fi

  sleep 5
done
EOS
chmod +x /usr/local/bin/ec-agent.sh

cat > /etc/systemd/system/ec-agent.service << 'EOF'
[Unit]
Description=EC native volume mount + termination watcher
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/ec-agent.sh
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable --now ec-agent.service

One service, two jobs, both idempotent: check whether /mnt/ecvol is mounted yet and mount it the moment multipath claims the LUN, and check whether this instance has a pending Terminate event. Either job is a no-op if there’s nothing to do, so the same loop just runs from first boot to eventual termination.

The Function#

The Function only knows about two things: the PureStorage.Block REST API, and whatever instance calls its two HTTP routes. It has no idea a VMSS is involved.

import logging, os, time
import azure.functions as func
import requests
from azure.identity import DefaultAzureCredential

app = func.FunctionApp()
ARM = "https://management.azure.com"
STORAGE_POOL_ID = os.environ["STORAGE_POOL_ID"]
VG_API = os.environ["VOLUME_GROUP_API_VERSION"]
VOL_API = os.environ["VOLUME_API_VERSION"]
MOUNT_API = os.environ["MOUNT_DATA_API_VERSION"]
VOL_SIZE_BYTES = int(os.environ["VOL_SIZE_BYTES"])
VMSS_NAME = os.environ["VMSS_NAME"]
VMSS_ID = os.environ["VMSS_ID"]
SHARED_SECRET = os.environ["SHARED_SECRET"]
_credential = DefaultAzureCredential()

def _token(): return _credential.get_token(f"{ARM}/.default").token
def _headers(): return {"Authorization": f"Bearer {_token()}", "Content-Type": "application/json"}
def _authorized(req): return req.headers.get("x-shared-secret") == SHARED_SECRET
def _exists(url, api_version):
    return requests.get(url, params={"api-version": api_version}, headers=_headers()).status_code == 200

def _names(vm_id):
    key = vm_id.replace("-", "")[:12]
    return f"vg-{VMSS_NAME}-{key}", f"vol-{VMSS_NAME}-{key}"

def _wait_succeeded(url, api_version, attempts=18, delay=5):
    for _ in range(attempts):
        resp = requests.get(url, params={"api-version": api_version}, headers=_headers())
        if resp.status_code == 404:
            time.sleep(delay); continue
        resp.raise_for_status()
        body = resp.json()
        props = body.get("properties", {})
        if "provisioningState" not in props:
            return body  # Volumes never report one -- a 200 body means done
        state = props["provisioningState"]
        if state == "Succeeded": return body
        if state == "Failed": raise RuntimeError(f"{url} provisioning failed: {body}")
        time.sleep(delay)
    raise TimeoutError(f"{url} did not reach Succeeded in time")

def _create_volume_group_and_volume(vm_id):
    vg_name, vol_name = _names(vm_id)
    vg_url = f"{ARM}{STORAGE_POOL_ID}/volumeGroups/{vg_name}"
    if not _exists(vg_url, VG_API):
        requests.put(vg_url, params={"api-version": VG_API}, headers=_headers(),
                     json={"location": "westus2", "properties": {"performanceParameters": {}}})
    _wait_succeeded(vg_url, VG_API)

    vol_url = f"{vg_url}/volumes/{vol_name}"
    if not _exists(vol_url, VOL_API):
        requests.put(vol_url, params={"api-version": VOL_API}, headers=_headers(),
                     json={"properties": {"provisionedSize": VOL_SIZE_BYTES}})
    _wait_succeeded(vol_url, VOL_API)

    conn = requests.post(f"{vg_url}/listConnectionParameters", params={"api-version": MOUNT_API}, headers=_headers())
    conn.raise_for_status()
    return conn.json()

def _mount_on_instance(instance_id, endpoints):
    ext_url = f"{ARM}{VMSS_ID}/virtualMachines/{instance_id}/extensions/MountIscsiLinux-deploy"
    targets = [{"ip": e["ip"], "port": 3260, "iqn": e["iqn"]} for e in endpoints]
    requests.put(ext_url, params={"api-version": "2024-07-01"}, headers=_headers(), json={
        "properties": {
            "publisher": "PureStorage.Extensions", "type": "MountIscsiLinux",
            "typeHandlerVersion": "1.3", "autoUpgradeMinorVersion": True,
            "settings": {"targets": targets, "replaceTargets": False, "sessionCount": 2, "reboot": False},
        }
    }).raise_for_status()

def _delete_volume_and_group(vm_id):
    vg_name, vol_name = _names(vm_id)
    vg_url = f"{ARM}{STORAGE_POOL_ID}/volumeGroups/{vg_name}"
    for url, api in [(f"{vg_url}/volumes/{vol_name}", VOL_API), (vg_url, VG_API)]:
        resp = requests.delete(url, params={"api-version": api}, headers=_headers())
        if resp.status_code not in (200, 202, 204, 404):
            resp.raise_for_status()

@app.function_name(name="provision")
@app.route(route="provision", methods=["POST"], auth_level=func.AuthLevel.ANONYMOUS)
def provision(req: func.HttpRequest) -> func.HttpResponse:
    if not _authorized(req):
        return func.HttpResponse("unauthorized", status_code=401)
    vm_id, instance_id = req.params.get("vmId"), req.params.get("instanceId")
    if not vm_id or not instance_id:
        return func.HttpResponse("missing vmId or instanceId", status_code=400)
    try:
        conn_params = _create_volume_group_and_volume(vm_id)
        endpoints = conn_params.get("iscsi", {}).get("endpoints", [])
        if not endpoints:
            raise RuntimeError(f"no iSCSI endpoints returned: {conn_params}")
        _mount_on_instance(instance_id, endpoints)
    except Exception as exc:
        logging.exception("Provisioning failed for vmId=%s", vm_id)
        return func.HttpResponse(f"provisioning failed: {exc}", status_code=500)
    return func.HttpResponse("ok", status_code=200)

@app.function_name(name="deprovision")
@app.route(route="deprovision", methods=["POST"], auth_level=func.AuthLevel.ANONYMOUS)
def deprovision(req: func.HttpRequest) -> func.HttpResponse:
    if not _authorized(req):
        return func.HttpResponse("unauthorized", status_code=401)
    vm_id = req.params.get("vmId")
    if not vm_id:
        return func.HttpResponse("missing vmId", status_code=400)
    try:
        _delete_volume_and_group(vm_id)
    except Exception as exc:
        logging.exception("Deprovisioning failed for vmId=%s", vm_id)
        return func.HttpResponse(f"deprovisioning failed: {exc}", status_code=500)
    return func.HttpResponse("ok", status_code=200)

deprovision is the mirror image, deleting the volume then the volume group, both idempotent against a 404 so a retried delete call is a no-op instead of an error. A couple of real quirks in this code are worth their own explanation, in Lessons Learned below.

Watching It Work#

az vmss scale --name gso-ds-vmss01 --resource-group <rg> --new-capacity 2
az resource list --resource-group <pool-rg> --resource-type "PureStorage.Block/storagePools/volumeGroups" -o table

Name                                       Status
-----------------------------------------  ---------
gso-ds-sp01/vg-gso-ds-vmss01-78dd5e24fb27  Succeeded
gso-ds-sp01/vg-gso-ds-vmss01-5105cb35cedb  Succeeded

Both instances end up with their own volume group, volume, a succeeded MountIscsiLinux-deploy extension, and /mnt/ecvol actually mounted and writable, entirely on their own, no coordination between them.

Scale back in and the termination watcher fires on its own:

az vmss scale --name gso-ds-vmss01 --resource-group <rg> --new-capacity 0
# both volume groups are gone within seconds of their instances actually terminating

Deleted volume groups land in a three-day recoverable window before Azure eradicates them for good, same as the manual terraform destroy case from the earlier post. If you want them gone immediately, that’s a separate call against recoverableVolumeGroups.

The real test, after fixing the Resources bug above, was scaling to 10 and back down to 0 a few times in a row:

az vmss scale --name gso-ds-vmss01 --resource-group <rg> --new-capacity 10
az resource list --resource-group <pool-rg> --resource-type "PureStorage.Block/storagePools/volumeGroups" -o table | grep -c vmss01
# 10

All ten came up independently, all ten mounted, and the count held steady through the whole run instead of collapsing the moment Azure’s scale-in logic touched any two of them. Scaling back to 0 cleaned up all ten on their own, no leftovers in the pool.

Lessons Learned#

A few of these are already implied by the code above, but they’re worth pulling out on their own since they’ll bite you outside this specific project too.

There’s no Event Grid trigger for a VMSS instance being created or deleted. I built the whole first pass of this project around two event types I was sure existed: Microsoft.Compute.VMSS.InstanceCreated and Microsoft.Compute.VMSS.InstanceDeleted. Wired up an Event Grid system topic scoped to the VMSS, subscribed an Azure Function, scaled the set out to test it. Nothing fired, zero on PublishSuccessCount, checked over a full day. Turns out this is the only event type that topic actually supports:

az eventgrid topic-type list-event-types --name Microsoft.Compute.VirtualMachineScaleSets -o table

Description                                   DisplayName                      Name
--------------------------------------------  -------------------------------  -------------------------------------------------------------
Published when Lifecycle Hooks are triggered  Lifecycle Hook Events (Preview)  Microsoft.Compute.VirtualMachineScaleSets.LifecycleHookEvents

That’s tied to VMSS Lifecycle Hooks, which is still in preview and only covers graceful scale-in termination. There is no Event Grid signal for an instance being created, and nothing GA for deletion either. The event types I’d built against simply don’t exist. Good thing to find out from a live test rather than a design doc, and the reason everything else in this post is a pull model instead of a push.

Scheduled Events on a scale set aren’t scoped to the instance polling them. The first version of the termination watcher matched on EventType=="Terminate" alone:

EVENTIDS=$(echo "$EVENTS" | jq -r '.Events[] | select(.EventType=="Terminate") | .EventId')

Scaled a set from 11 instances down to 10. Azure’s scale-in picked two instances to remove to rebalance fault domains, which is normal. What wasn’t normal: every other instance in the set called /api/deprovision on itself within the same few seconds, deleting nine live, in-use volumes while their VMs kept running untouched. Each event carries a Resources array naming which VM it actually applies to, and I never checked it, so every instance polling IMDS at that moment saw an event with EventType=="Terminate" show up in its own feed and reacted as if it were the target. Fixed by checking that field before acting on anything:

EVENTIDS=$(echo "$EVENTS" | jq -r --arg self "$SELF" \
  '.Events[] | select(.EventType=="Terminate" and (.Resources | index($self) != null)) | .EventId')

$SELF is just hostname output, captured once at boot. Re-ran the same scale-to-10 test afterward and the volume count held steady through the whole cycle. If you’re writing anything against Scheduled Events on a scale set, this is the one line that matters: the feed is shared, the events aren’t yours by default, and .Resources is what makes them yours.

MountIscsiLinux doesn’t format or mount anything, despite the name. It establishes the iSCSI sessions and hands the LUN to multipathd, full stop. Checking df -h right after the extension reports success shows exactly what you’d expect if you stopped there: nothing but Azure’s own ephemeral resource disk at /mnt. What it did do is visible with multipath -ll, four active iSCSI sessions (two controllers, two paths each) collapsed into one /dev/mapper/<wwid> device. That’s the device ec-agent.sh waits for, formats once, and mounts, the same mkfs.ext4 / mount you’d run by hand if you were setting this up on a single VM.

reboot: true is a Windows setting, not a Linux one, and I copied it over without checking. The single-VM post this one follows up on sets reboot = true only for the Windows extension, because Windows’ iSCSI initiator service needs a restart to pick up new targets. Linux’s iscsid doesn’t need that, and the Linux settings in that same post leave it null. I carried reboot: true into this project’s Linux-only code anyway, assumed it would restart the instance, and built the termination watcher as a systemd service specifically so it would survive that restart. It turned out to be a harmless no-op, not a bug: cloud-init’s own uptime counter never reset during a successful mount, and even the original nohup-based version of the watcher, before I ever touched systemd, survived long enough to clean up its volume every time it was tested. No reboot ever actually happened. Fixed by setting it to false, since there’s no reason to ask for a restart Linux doesn’t need.

The systemd service was the right call anyway, just for the wrong reason at the time. A termination watcher needs to run reliably for the entire life of the instance, survive being killed and restarted, and be inspectable with systemctl status and journalctl instead of disappearing into a background shell with no trace. That’s worth having regardless of whether anything ever reboots.

The RP rejects a PUT on a resource that already exists, with a ResourceCreationValidateFailed 400, rather than treating it as an update. A retried boot call has to check first, not just PUT and hope.

Volumes don’t return a provisioningState at all. A VolumeGroup does, and it’s worth polling for Succeeded. A Volume comes back with a body (serial number, space usage) the instant it exists, full stop, so waiting on a provisioningState field that will never appear just burns your Function’s timeout.

The shared secret is fine for a lab, not for production. It’s baked into custom_data, which is readable by anyone with read access to the VMSS resource. The right long-term answer is the VMSS’s own managed identity validated against the Function’s Easy Auth / AAD config.

Wrapping Up#

Event Grid seemed like the obvious answer here and turned out not to exist for this at all, which is really what this post is about: two IMDS calls, an Azure Function, and the vendor extension end up doing what Event Grid couldn’t. Took a couple of real bugs to get there, but it held up clean through a 10-instance scale-out and back down, nothing left behind in the pool.
