Multi-AZ Scaling for Everpure Cloud Azure Native Volumes on a VMSS

September 25, 2026 · 13 min read · 2672 words
Share

Are you running a scale set across availability zones and need every instance’s volume to live in the same zone as the instance? In Part 1 every instance got its own Everpure Cloud Azure Native volume on scale-out and cleaned it up on scale-in, but it all hung off a single storage pool in a single zone. This time I spread the scale set across two zones, gave each zone its own pool, and made sure an instance only ever attaches to the pool it shares a zone with.

Disclaimer: this is a proof of concept showing what’s possible on Everpure Cloud Azure Native, not an officially supported pattern. I built it and validated it end to end against live pools in two availability zones, including a 10-instance scale test split 5 and 5, so I know it works. The shared-secret auth, the naming scheme, error handling, all of it is lab-grade. Treat this as a working example to build your own version from, not something to drop straight into production.

Why Zones Change Things#

A storage pool is pinned to one availability zone when you create it. A scale set spread across zones 1 and 2 will put roughly half its instances somewhere other than that pool. An instance in zone 2 can still reach a pool in zone 1 over iSCSI, it literally works, but every I/O is now crossing zones and losing zone 1 takes out storage for instances that were supposed to survive it. That’s not what you spread across zones for.

So the rule for this build is simple: an instance attaches to the pool in its own zone, and if there isn’t one, it attaches nothing. No reaching across.

I had just stood up a new Everpure Cloud service in UK South, so this all got built fresh there instead of bolted onto the Part 1 lab.

The Layout#

  • One VNet, with a VM subnet for the scale set and a NAT gateway for outbound
  • One delegated subnet and one storage pool per availability zone, both on the same reservation
  • A Uniform scale set spread across zones 1 and 2
  • The same orchestrator Function from Part 1, now on Flex Consumption, deciding which pool each instance gets
  • Azure Bastion, so I can get onto an instance without a public IP

Prerequisites#

  • An Everpure Cloud reservation in a region with availability zones
  • A VM size available in every zone you plan to use. Check this first, more on that in Design Notes
  • Terraform, with the azapi, azurerm, and random providers
  • The Azure CLI logged in, for the Function zip deploy and the Resource Graph queries

Project Structure#

There are two Terraform roots now. The network and pools take about 30 minutes to build and almost never change, so they live apart from the scale set, which I tear down and rebuild constantly.

vmss-ec-native-multi-az/

│   ├── network.tf           # VNet, VM subnet, NAT gateway, delegated subnet per zone
│   ├── pool.tf              # one storage pool per zone
│   ├── bastion.tf
│   └── terraform.auto.tfvars.example
└── vmss/

The Network and Pools#

The pools are described as a map keyed by zone, so adding a third zone later is one more line:

storage_pools = {
  "1" = { name = "gso-ds-uks-sp01", subnet_cidr = "172.19.1.0/27", bandwidth = 800 }
  "2" = { name = "gso-ds-uks-sp02", subnet_cidr = "172.19.1.32/27", bandwidth = 800 }
}

Each pool gets its own subnet, delegated to PureStorage.Block/storagePools:

resource "azurerm_subnet" "storage" {
  for_each = var.storage_pools

  name                 = "${var.prefix}-subnet-storage-az${each.key}"
  resource_group_name  = azurerm_resource_group.rg.name
  virtual_network_name = azurerm_virtual_network.vnet.name
  address_prefixes     = [each.value.subnet_cidr]

  delegation {
    name = "PureStorage.Block/storagePools"
    service_delegation {
      name    = "PureStorage.Block/storagePools"
      actions = ["Microsoft.Network/virtualNetworks/subnets/join/action"]
    }
  }
}

The pool itself is the same azapi_resource from Provisioning Everpure Cloud Azure Native Resources with Terraform , with for_each over the same map and the zone coming from the key:

resource "azapi_resource" "storage_pool" {
  for_each = var.storage_pools

  type                      = "PureStorage.Block/storagePools@${local.pool_api_version}"
  name                      = each.value.name
  location                  = var.location
  parent_id                 = azurerm_resource_group.rg.id
  tags                      = var.tags
  schema_validation_enabled = true

  body = {
    properties = {
      availabilityZone             = each.key
      provisionedBandwidthMbPerSec = each.value.bandwidth
      reservationResourceId        = var.reservation_id
      vnetInjection = {
        subnetId = azurerm_subnet.storage[each.key].id
        vnetId   = azurerm_virtual_network.vnet.id
      }
    }
  }

  timeouts {
    create = "90m"
    update = "90m"
    delete = "90m"
    read   = "5m"
  }

  lifecycle {
    ignore_changes = [tags]
  }
}

Both pools came up in parallel in about 30 minutes. The VM subnet also gets a NAT gateway, since a brand new VNet has no default outbound access and the instances need to reach apt and the Function on boot.

Mapping Zones to Pools#

On the scale set side, the pools are looked up the same way, keyed by zone:

storage_pools_by_zone = {
  "1" = { name = "gso-ds-uks-sp01", resource_group = "gso-fsa-ds-uksouth" }
  "2" = { name = "gso-ds-uks-sp02", resource_group = "gso-fsa-ds-uksouth" }
}
zones = ["1", "2"]

data "azapi_resource" "storage_pool" {
  for_each  = var.storage_pools_by_zone
  type      = "PureStorage.Block/storagePools@2024-11-01-preview"
  name      = each.value.name
  parent_id = "/subscriptions/${var.subscription_id}/resourceGroups/${each.value.resource_group}"
}

The scale set gets zones = var.zones, and the Function gets the whole map as one JSON app setting:

"STORAGE_POOL_IDS_BY_ZONE" = jsonencode({ for zone, pool in data.azapi_resource.storage_pool : zone => pool.id })

The Function’s managed identity doesn’t need Contributor or Virtual Machine Contributor for any of this. It needs a handful of volume group and volume operations on each pool, and read plus extension write on the scale set. So it gets two custom roles with exactly those actions, assigned to each pool and to the one scale set:

resource "azurerm_role_definition" "orch_storage" {
  name        = "EC native volume orchestrator (${var.vmss_name})"
  scope       = "/subscriptions/${var.subscription_id}"
  description = "Create, read and delete Everpure Cloud Azure Native volume groups and volumes in a storage pool."

  permissions {
    actions = [
      "PureStorage.Block/storagePools/read",
      "PureStorage.Block/storagePools/volumeGroups/read",
      "PureStorage.Block/storagePools/volumeGroups/write",
      "PureStorage.Block/storagePools/volumeGroups/delete",
      "PureStorage.Block/storagePools/volumeGroups/listConnectionParameters/action",
      "PureStorage.Block/storagePools/volumeGroups/volumes/read",
      "PureStorage.Block/storagePools/volumeGroups/volumes/write",
      "PureStorage.Block/storagePools/volumeGroups/volumes/delete",
    ]
  }

  assignable_scopes = local.pool_rg_ids
}

resource "azurerm_role_definition" "orch_vmss" {
  name        = "EC native VMSS extension orchestrator (${var.vmss_name})"
  scope       = "/subscriptions/${var.subscription_id}"
  description = "Read VMSS instances and manage their VM extensions."

  permissions {
    actions = [
      "Microsoft.Compute/virtualMachineScaleSets/read",
      "Microsoft.Compute/virtualMachineScaleSets/virtualMachines/read",
      "Microsoft.Compute/virtualMachineScaleSets/virtualMachines/extensions/read",
      "Microsoft.Compute/virtualMachineScaleSets/virtualMachines/extensions/write",
    ]
  }

  assignable_scopes = [data.azurerm_resource_group.lab.id]
}

resource "azurerm_role_assignment" "orch_storage_pool" {
  for_each           = data.azapi_resource.storage_pool
  scope              = each.value.id
  role_definition_id = azurerm_role_definition.orch_storage.role_definition_resource_id
  principal_id       = azurerm_function_app_flex_consumption.orchestrator.identity[0].principal_id
}

resource "azurerm_role_assignment" "orch_vmss" {
  scope              = azurerm_linux_virtual_machine_scale_set.lab.id
  role_definition_id = azurerm_role_definition.orch_vmss.role_definition_resource_id
  principal_id       = azurerm_function_app_flex_consumption.orchestrator.identity[0].principal_id
}

The action names come straight from az provider operation show --namespace PureStorage.Block. Creating custom roles needs Microsoft.Authorization/roleDefinitions/write at the subscription, so whoever runs the apply needs Owner or User Access Administrator there.

Routing in the Function#

The instance already sends its instance ID on boot. The Function uses that to read the instance’s zone straight from ARM, instead of trusting a zone the caller sends it:

POOLS_BY_ZONE = json.loads(os.environ["STORAGE_POOL_IDS_BY_ZONE"])

def _instance_zone(instance_id: str) -> str | None:
    resp = requests.get(_instance_url(instance_id), params={"api-version": COMPUTE_API}, headers=_headers())
    resp.raise_for_status()
    zones = resp.json().get("zones") or []
    return zones[0] if zones else None

Then provision picks the pool for that zone, and if there isn’t one it returns without creating anything:

zone = _instance_zone(instance_id) or "none"
pool_id = POOLS_BY_ZONE.get(zone)

if not pool_id:
    # No same-zone pool: attach nothing rather than reaching across zones.
    logging.warning("No storage pool for zone %s (instance %s); skipping", zone, instance_id)
    return func.HttpResponse(f"no storage pool for zone {zone}; skipped", status_code=200)

I tested the skip path in my first lab, where I only had a pool in zone 1. The zone 1 instances got volumes and the zone 2 instances booted clean with nothing attached, which is exactly what I wanted.

deprovision only gets a vmId, so instead of looking up the zone again it just sweeps every pool in the map. Deletes are 404-safe, so a pool that never had this instance’s volume group is a no-op.

Labeling Without Instance Tags#

Once you have two pools, the next question is always “which pool is this instance on?” My first idea was to tag the VM with its zone, pool, and volume group. That doesn’t work on a Uniform scale set. A PATCH on an instance’s tags returns a 405, and a PUT returns 200 and silently drops the tags. Instances in Uniform mode just don’t carry their own tags.

So the volume group carries the mapping instead:

"tags": {
    "vmss": VMSS_NAME,
    "vm-name": f"{VMSS_NAME}_{instance_id}",
    "instance-id": instance_id,
    "vm-id": vm_id,
    "zone": zone,
    "storage-pool": pool_id.rstrip("/").split("/")[-1],
},

vm-name is the same compute.name string from Part 1 (like gso-ds-vmss01_11), which is also what the VM is called in Azure Resource Graph. Resource Graph indexes the PureStorage.Block volume groups too, so one query joins the two and shows every instance next to its zone, pool, and volume group. It also calls out anything that doesn’t line up:

resources
| where type =~ 'purestorage.block/storagepools/volumegroups' and tags['vmss'] == 'gso-ds-vmss01'
| project vm = tostring(tags['vm-name']), vgZone = tostring(tags['zone']), pool = tostring(tags['storage-pool']), vg = name
| join kind=fullouter (
    computeresources
    | where type =~ 'microsoft.compute/virtualmachinescalesets/virtualmachines'
      and id contains '/virtualMachineScaleSets/gso-ds-vmss01/'
    | project vmName = name, vmZone = tostring(zones[0])
  ) on $left.vm == $right.vmName
| extend status = case(
    isempty(vmName), 'ORPHAN - no instance',
    isempty(vg), 'no volume',
    vgZone != vmZone, 'ZONE MISMATCH',
    'ok')
| project vm = coalesce(vm, vmName), vmZone, pool, vg, status
| order by pool asc, vm asc

That pastes straight into Resource Graph Explorer, or runs with az graph query -q. The ORPHAN status also doubles as a check that scale-in cleaned up after itself.

Coordinated Scale-In#

On a scale set, Scheduled Events work a little differently than on a single VM, and the scale-in side is built around two things about them. When Azure removes several instances at once, it can list all of them in one Terminate event. And per the Scheduled Events docs , approving an event releases every VM in its Resources list, not just the one that approved it. Once approved, the event stays in the feed with an EventStatus of Started until the instances are gone.

So every instance in an event needs to finish cleaning up before anyone approves it. The agent handles that in two steps. Each instance deprovisions itself exactly once, whatever state the event is in, and only approves once every instance named in the event is done:

EVENT=$(curl -s -H "Metadata:true" "$IMDS/scheduledevents?$SE_API" | jq -c --arg self "$SELF" \
  'first(.Events[] | select(.EventType=="Terminate" and (.Resources | index($self) != null))) // empty')

if [ -n "$EVENT" ]; then
  EID=$(echo "$EVENT" | jq -r '.EventId')
  STATUS=$(echo "$EVENT" | jq -r '.EventStatus')
  NAMES=$(echo "$EVENT" | jq -r '.Resources | join(",")')

  if [ ! -f "$DONE" ]; then
    log "terminate $EID status=$STATUS resources=$NAMES"
    CODE=$(curl -s -o /var/log/ec-deprovision.json -w '%%{http_code}' -X POST \
      -H "x-shared-secret: $SECRET" "$FUNC_URL/api/deprovision?vmId=$VMID")
    log "deprovision http=$CODE"
    [ "$CODE" = "200" ] && touch "$DONE"
  fi

  if [ -f "$DONE" ] && [ "$STATUS" = "Scheduled" ] && [ ! -f "$DONE.$EID" ]; then
    PENDING=$(curl -s -H "x-shared-secret: $SECRET" "$FUNC_URL/api/pending?vmNames=$NAMES" | jq -r '.pending | length')
    if [ "$PENDING" = "0" ]; then
      CODE=$(curl -s -o /dev/null -w '%%{http_code}' -X POST -H "Metadata:true" -H "Content-Type: application/json" \
        -d "{\"StartRequests\":[{\"EventId\":\"$EID\"}]}" "$IMDS/scheduledevents?$SE_API")
      log "approve $EID http=$CODE"
      [ "$CODE" = "200" ] && touch "$DONE.$EID"
    fi
  fi
fi

The %%{http_code} is doubled because this lives in a Terraform templatefile, where %{ starts a directive.

The /api/pending route is where the volume group tags pay off a second time. It takes the instance names from the event and checks whether any of them still own a live volume group:

def _pending_vm_names(vm_names: set[str]) -> list[str]:
    pending = []
    for pool_id in POOLS_BY_ZONE.values():
        url = f"{ARM}{pool_id}/volumeGroups"
        params = {"api-version": VG_API}
        while url:
            resp = requests.get(url, params=params, headers=_headers())
            resp.raise_for_status()
            body = resp.json()
            for vg in body.get("value", []):
                name = (vg.get("tags") or {}).get("vm-name")
                state = vg.get("properties", {}).get("provisioningState")
                if name in vm_names and state != "Deleting":
                    pending.append(name)
            url, params = body.get("nextLink"), None
    return pending

A volume group that’s already Deleting counts as done, since the delete has been issued and doesn’t need the instance to stay up for it. If an instance can’t clean up for some reason, nobody approves and Azure proceeds on its own when the five-minute termination_notification timeout runs out. The ORPHAN status in the mapping query catches anything left behind in that case.

To watch a scale-in from the instance’s side, I opened a Bastion tunnel to one instance, kicked off the scale-in, and polled its view of Scheduled Events and its agent log every 10 seconds until it dropped off:

az network bastion tunnel --name <bastion> --resource-group <rg> \
  --target-resource-id <vmss-id>/virtualMachines/<instanceId> --resource-port 22 --port 2201 &

ssh -i vmss_lab_key -p 2201 azureuser@127.0.0.1 \
  'curl -s -H Metadata:true "http://169.254.169.254/metadata/scheduledevents?api-version=2020-07-01" | jq -c ".Events"; sudo tail -5 /var/log/ec-agent.log'

Scaling 10 instances to 0, every volume group was gone within about 90 seconds of the scale-in starting and the mapping query came back empty afterwards. From one instance, the whole sequence takes about seven seconds:

17:05:39Z terminate 5589F49D-... status=Scheduled resources=gso-ds-vmss01_26
17:05:45Z deprovision http=200
17:05:46Z approve 5589F49D-... http=200

The scale-in itself still takes about five minutes end to end. The approval returns a 200 and the guest drops off the network about 35 seconds later, but the instance doesn’t leave the scale set until the event’s NotBefore time. The docs say approving lets Azure shorten the wait “when possible,” and for scale set terminations it holds to the full window. Five minutes is the minimum termination_notification timeout, so plan on about five minutes per scale-in.

Watching It Work#

az vmss scale --name gso-ds-vmss01 --resource-group <rg> --new-capacity 10
az vmss list-instances --name gso-ds-vmss01 --resource-group <rg> --query "[].zones[0]" -o tsv | sort | uniq -c

   5 1
   5 2

Azure balanced the ten instances five and five on its own. Within about a minute of boot every instance had a volume group in its own zone’s pool:

Design Notes#

The Function runs on Flex Consumption. It’s the current consumption plan for Azure Functions, and it doesn’t depend on Linux Consumption (Y1) quota, which is zero in some regions. In Terraform that’s azurerm_function_app_flex_consumption with a blob container for deployments and runtime_name/runtime_version for Python 3.11. Flex sets the worker runtime itself, so FUNCTIONS_WORKER_RUNTIME stays out of the app settings. The zip deploy with --build-remote true is the same as Part 1.

The VM size has to exist in every zone. Size restrictions are per zone, not per region, so I check with az vm list-skus --location <region> --size <size> before picking one. Standard_B2s_v2 is available in all three zones in the regions I used.

The VM subnet has a NAT gateway. A new VNet has no default outbound access, and the boot script needs it for apt and the call to the Function.

The mapping lives on the volume group. Uniform scale set instances don’t carry their own tags, so the volume group tags are the source of truth. The Resource Graph query and /api/pending both read them.

Terraform ignores instances. Scaling is done by hand here, or by autoscale in a real deployment, so ignore_changes = [instances] keeps an unrelated terraform apply from resetting the instance count.

Wrapping Up#

The zone routing ended up being the easy part: a map of zones to pools and one ARM call to read the instance’s zone. The part that took real testing was scale-in, and the volume group tags ended up doing double duty, answering “which pool is this instance on” and “is everyone in this event cleaned up yet” from the same data.
