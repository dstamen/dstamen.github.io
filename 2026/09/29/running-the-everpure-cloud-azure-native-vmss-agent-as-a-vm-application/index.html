Running the Everpure Cloud Azure Native VMSS Agent as a VM Application

September 29, 2026 · 12 min read · 2536 words
Share

Are you looking for a way to give every scale set instance its own Everpure Cloud Azure Native volume without running an Azure Function next to it? In Part 1 and Part 2 an orchestrator Function did the storage work while each instance called it on boot and on scale-in. This time the instance does all of it itself, and the agent that does it ships as a VM Application from an Azure Compute Gallery. I ran it on a single pool in one zone first, then across two zones with a pool in each.

Disclaimer: this is a proof of concept showing what’s possible on Everpure Cloud Azure Native, not an officially supported pattern. I built it and validated it end to end, including 10-instance scale tests in one zone and across two, so I know it works. The naming scheme, error handling, all of it is lab-grade. Treat this as a working example to build your own version from, not something to drop straight into production.

Why Drop the Function#

The Function worked, but it was a second thing to run. It had its own plan, its own storage account, a separate zip deploy, and a shared secret baked into custom_data so the instances could call it. When I looked at what it actually did, almost all of it was something the instance could do for itself:

The Function didThe instance does it with
Read the instance’s zone from ARMcompute.zone from IMDS
Create and delete the volume group and volumethe same REST calls, with a token for the scale set’s managed identity
Call listConnectionParameterssame call, same identity
Push MountIscsiLinux onto the instancea PUT on its own instance’s extension
Check if everyone in a Terminate event is cleaned uplist the pool’s volume groups and check the vm-name tags
Hold config in app settingsthe scale set’s userData

The scale-in logic already lived on the instance. So the move is really about the create path, plus getting the agent onto every instance without a pile of custom_data. That’s what VM Applications are for: a versioned package in an Azure Compute Gallery that the scale set installs on every instance.

The same code covers one zone or several. The config carries the zone-to-pool map from Part 2. With one pool it has a single entry and the scale set is pinned to that pool’s zone, and going multi-AZ is two more lines of config.

How It Works#

  1. The instance boots and the VM Application extension installs ec-agent. The install step copies two files and starts a systemd service, then returns.
  2. The agent reads its config from userData and its identity from IMDS, then gets an ARM token for the scale set’s user-assigned identity.
  3. It creates its volume group and volume in the pool for its zone, gets the iSCSI endpoints, and pushes MountIscsiLinux onto itself.
  4. Once multipath has the LUN it formats it and mounts it at /mnt/ecvol.
  5. On scale-in it sees its Terminate event, deletes its volume and volume group, and approves the event once everyone in it is done.

There’s no Function, no storage account for it, and no shared secret anywhere.

Prerequisites#

  • An existing storage pool (one per zone for multi-AZ, same as Part 2) and a VNet and subnet that can reach it
  • Outbound access from that subnet, since the agent installs jq and multipath-tools with apt
  • Terraform with the azurerm, azapi, archive, and random providers
  • Permission to create custom roles at the subscription (Owner or User Access Administrator)

Project Structure#

The Identity and Roles#

Every instance authenticates as the scale set’s user-assigned identity, so that’s where the roles go:

resource "azurerm_user_assigned_identity" "agent" {
  name                = "${var.vmss_name}-agent"
  resource_group_name = azurerm_resource_group.lab.name
  location            = var.location
  tags                = var.tags
}

It gets the same two custom roles as Part 2. The storage one is assigned on the pool:

resource "azurerm_role_definition" "agent_storage" {
  name        = "EC native volume agent (${var.vmss_name})"
  scope       = "/subscriptions/${var.subscription_id}"
  description = "Create, read and delete Everpure Cloud Azure Native volume groups and volumes in a storage pool."

  permissions {
    actions = [
      "PureStorage.Block/storagePools/read",
      "PureStorage.Block/storagePools/volumeGroups/read",
      "PureStorage.Block/storagePools/volumeGroups/write",
      "PureStorage.Block/storagePools/volumeGroups/delete",
      "PureStorage.Block/storagePools/volumeGroups/listConnectionParameters/action",
      "PureStorage.Block/storagePools/volumeGroups/volumes/read",
      "PureStorage.Block/storagePools/volumeGroups/volumes/write",
      "PureStorage.Block/storagePools/volumeGroups/volumes/delete",
    ]
  }

  assignable_scopes = local.pool_rg_ids
}

The compute one is assigned on the scale set. It has one action the Function version didn’t need, instanceView/read, which I’ll get to in the agent section:

resource "azurerm_role_definition" "agent_vmss" {
  name        = "EC native VMSS extension agent (${var.vmss_name})"
  scope       = "/subscriptions/${var.subscription_id}"
  description = "Read VMSS instances and their instance view, and manage their VM extensions."

  permissions {
    actions = [
      "Microsoft.Compute/virtualMachineScaleSets/read",
      "Microsoft.Compute/virtualMachineScaleSets/virtualMachines/read",
      "Microsoft.Compute/virtualMachineScaleSets/virtualMachines/instanceView/read",
      "Microsoft.Compute/virtualMachineScaleSets/virtualMachines/extensions/read",
      "Microsoft.Compute/virtualMachineScaleSets/virtualMachines/extensions/write",
    ]
  }

  assignable_scopes = [azurerm_resource_group.lab.id]
}

Publishing the Agent as a VM Application#

A VM Application is a package in blob storage, published into a Compute Gallery as a version. Terraform zips the app/ folder and uploads it:

data "archive_file" "agent" {
  type        = "zip"
  source_dir  = "${path.module}/app"
  output_path = "${path.module}/.build/ec-agent-${var.app_version}.zip"
}

resource "azurerm_storage_blob" "agent" {
  name                   = "ec-agent-${var.app_version}.zip"
  storage_container_id   = azurerm_storage_container.pkg.id
  type                   = "Block"
  source                 = data.archive_file.agent.output_path
  content_md5            = data.archive_file.agent.output_md5

  lifecycle {
    create_before_destroy = true
  }
}

Then the gallery, the application, and a version that points at the blob through a short-lived read SAS. The gallery copies the package in when the version is created, so the SAS only has to live long enough for that:

resource "azurerm_shared_image_gallery" "gallery" {
  name                = var.gallery_name
  resource_group_name = azurerm_resource_group.lab.name
  location            = var.location
}

resource "azurerm_gallery_application" "agent" {
  name              = "ec-agent"
  gallery_id        = azurerm_shared_image_gallery.gallery.id
  location          = var.location
  supported_os_type = "Linux"
}

resource "azurerm_gallery_application_version" "agent" {
  name                   = var.app_version
  gallery_application_id = azurerm_gallery_application.agent.id
  location               = var.location
  package_file           = "ec-agent.zip"

  manage_action {
    install = "python3 -m zipfile -e ec-agent.zip /opt/ec-agent && bash /opt/ec-agent/install.sh"
    update  = "python3 -m zipfile -e ec-agent.zip /opt/ec-agent && bash /opt/ec-agent/install.sh"
    remove  = "bash /opt/ec-agent/remove.sh"
  }

  source {
    media_link = "${azurerm_storage_blob.agent.url}${data.azurerm_storage_account_blob_container_sas.pkg.sas}"
  }

  target_region {
    name                   = var.location
    regional_replica_count = 1
    storage_account_type   = "Standard_LRS"
  }

  lifecycle {
    ignore_changes        = [source]
    create_before_destroy = true
  }
}

python3 -m zipfile does the unzip because Python is always on the Ubuntu image and unzip isn’t guaranteed to be. package_file renames the download to ec-agent.zip so the install command knows what it’s looking for. Publishing a version took three to four minutes each time.

The install script itself is short on purpose:

#!/bin/bash
set -euo pipefail
cd "$(dirname "$0")"

install -m 0755 ec-agent.sh /usr/local/bin/ec-agent.sh
install -m 0644 ec-agent.service /etc/systemd/system/ec-agent.service
systemctl daemon-reload
systemctl enable ec-agent.service
systemctl restart --no-block ec-agent.service

It lays the files down, starts the service without waiting on it, and exits. More on why in Design Notes.

The Scale Set#

The scale set carries the identity, the config, and the termination notification:

resource "azurerm_linux_virtual_machine_scale_set" "lab" {
  name                = var.vmss_name
  resource_group_name = azurerm_resource_group.lab.name
  location            = var.location
  sku                 = var.vm_size
  instances           = var.instance_count
  upgrade_mode        = "Manual"
  zones               = var.zones

  identity {
    type         = "UserAssigned"
    identity_ids = [azurerm_user_assigned_identity.agent.id]
  }

  user_data = base64encode(jsonencode(local.agent_config))

  termination_notification {
    enabled = true
    timeout = "PT5M"
  }

  # admin user, image, os_disk and network_interface are the same as Part 1

  lifecycle {
    ignore_changes = [instances, gallery_application]
  }
}

The config in userData is everything the agent needs and nothing secret:

agent_config = {
  vmss         = var.vmss_name
  location     = var.location
  volSizeBytes = var.vol_size_bytes
  clientId     = azurerm_user_assigned_identity.agent.client_id
  pools        = { for zone, pool in data.azapi_resource.storage_pool : zone => pool.id }
  vgApi        = "2026-01-01-preview"
  volApi       = "2026-05-01-preview"
  mountApi     = "2026-05-01-preview"
  computeApi   = "2024-07-01"
}

The VM Application gets attached with a PATCH instead of the gallery_application block on the scale set resource:

resource "azapi_update_resource" "vmss_apps" {
  type        = "Microsoft.Compute/virtualMachineScaleSets@2024-07-01"
  resource_id = azurerm_linux_virtual_machine_scale_set.lab.id

  body = {
    properties = {
      virtualMachineProfile = {
        applicationProfile = {
          galleryApplications = [{
            packageReferenceId = azurerm_gallery_application_version.agent.id
            order              = 1
          }]
        }
      }
    }
  }
}

The azurerm provider marks gallery_application.version_id as force-new, so bumping the agent version through that block replaces the whole scale set. Azure itself updates the application profile in place, so the PATCH gets you a normal update and the scale set stays put.

The Agent#

The agent is one bash script running as a systemd service. On start it installs its packages, then reads who it is and what to do from IMDS:

META=$(curl -s -H Metadata:true "$IMDS/instance?api-version=2021-02-01")
CFG=$(curl -s -H Metadata:true "$IMDS/instance/compute/userData?api-version=2021-01-01&format=text" | base64 -d)

VMID=$(echo "$META" | jq -r .compute.vmId)
SELF=$(echo "$META" | jq -r .compute.name)
SELF_ID=$(echo "$META" | jq -r .compute.resourceId)
ZONE=$(echo "$META" | jq -r '.compute.zone // empty')
POOL=$(cfg ".pools[\"$ZONE\"] // empty")

Every ARM call uses a token for the scale set’s identity, straight from IMDS:

token() {
  curl -s -H Metadata:true \
    "$IMDS/identity/oauth2/token?api-version=2018-02-01&resource=https://management.azure.com/&client_id=$CLIENT_ID" |
    jq -r .access_token
}

The provision step is the same get-or-create the Function did, just in bash. The volume group gets the same tags as Part 2, so the Resource Graph mapping query from that post works unchanged:

if [ "$(arm GET "$vg_url?api-version=$VG_API")" != 200 ]; then
  body=$(jq -nc --arg loc "$LOCATION" --arg vmss "$VMSS" --arg name "$SELF" --arg iid "$INSTANCE_ID" \
    --arg vmid "$VMID" --arg zone "$ZONE" --arg pool "${POOL##*/}" \
    '{location: $loc,
      tags: {vmss: $vmss, "vm-name": $name, "instance-id": $iid, "vm-id": $vmid, zone: $zone, "storage-pool": $pool},
      properties: {performanceParameters: {}}}')
  c=$(arm PUT "$vg_url?api-version=$VG_API" "$body")
fi

Then the volume, listConnectionParameters, and the mount extension. Before it pushes the extension onto itself, it waits until nothing else on the instance is mid-operation:

wait_for_extensions_idle() {
  for _ in $(seq 1 60); do
    if [ "$(arm GET "$ARM$SELF_ID/instanceView?api-version=$COMPUTE_API")" = 200 ]; then
      busy=$(jq '[.extensions[]?.statuses[]?.code // empty | select(test("transitioning"; "i"))] | length' "$STATE/.body")
      [ "$busy" = 0 ] && return 0
    fi
    sleep 5
  done
}

That’s what the extra instanceView/read action is for. The VM Application itself installs through an extension, and two extension operations on the same instance at once is something I’ve seen wedge an instance before. Checking first keeps them from overlapping.

c=$(arm PUT "$ARM$SELF_ID/extensions/MountIscsiLinux-deploy?api-version=$COMPUTE_API" "$ext")

From there it’s the same loop as before: format and mount the multipath device once it shows up, and watch Scheduled Events for a Terminate naming this instance. Scale-in deletes the volume and volume group directly instead of calling the Function, and the pending check before approving lists the pool’s volume groups itself.

az vmss scale --name gso-ds-vmss03 --resource-group <rg> --new-capacity 10

All ten instances had a volume group within 83 seconds of the scale-out, and all ten mount extensions had succeeded at 168 seconds. From one instance’s agent log, the create path takes about 35 seconds once the agent starts, then about 50 more for the mount:

Going Multi-AZ#

Nothing in the agent or the Terraform changes for multiple zones. The zone map gets a second pool and the scale set gets a second zone:

storage_pools_by_zone = {
  "1" = { name = "gso-ds-uks-sp01", resource_group = "gso-fsa-ds-uksouth" }
  "2" = { name = "gso-ds-uks-sp02", resource_group = "gso-fsa-ds-uksouth" }
}
zones = ["1", "2"]

The storage role gets assigned on both pools through the same for_each, and every instance reads compute.zone from IMDS and picks its pool from the map. An instance in a zone with no entry gets no volume, same rule as Part 2.

I ran the same 10-instance test in UK South, against the two pools from Part 2. Azure split the instances five and five. Each pool had exactly its own zone’s five volume groups within 81 seconds, and all ten mount extensions had succeeded at 140 seconds.

The iSCSI sessions show each instance talking only to the pool in its own zone:

Shipping an Agent Update#

Changing the agent is a code change and a version bump:

app_version = "1.0.2"

terraform apply publishes the new version, PATCHes the scale set to reference it, and removes the old one. New instances get the new agent. Instances that are already running keep the version they installed until they’re upgraded, which with upgrade_mode = "Manual" is:

az vmss update-instances --name gso-ds-vmss03 --resource-group <rg> --instance-ids '*'

Design Notes#

The install step only installs. VM Applications install through an extension early in boot, while cloud-init is still running its own apt. So install.sh copies files and starts the service, and returns in seconds. The agent installs jq and multipath-tools itself, after waiting on cloud-init status --wait, and does all its ARM calls from the service, never from inside the install.

Config goes in userData, auth comes from the identity. userData is readable from IMDS and can change without rebuilding the image, which makes it a good home for the pool map and API versions. Nothing in it is a secret. The shared secret from the Function version is simply gone.

Each instance manages its own storage. Every instance’s identity can create and delete volume groups in its pool, so a compromised instance could delete a neighbor’s. That’s the same exposure the Function version had, where any instance holding the shared secret could ask the Function to deprovision any vmId.

The application reference is a PATCH. It keeps agent updates from replacing the scale set.

Wrapping Up#

The Function turned out to be doing work the instance could already do for itself. Moving it into a VM Application left one Terraform root, a versioned agent package, and a managed identity. It held up through 10-instance scale-outs in one zone and across two, and back down, with nothing left behind in any pool.
