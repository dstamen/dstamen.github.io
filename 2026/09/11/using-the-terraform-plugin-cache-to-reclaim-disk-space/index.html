Using the Terraform Plugin Cache to Reclaim Disk Space

September 11, 2026 · 6 min read · 1074 words
Share

Are you wondering where all your disk space went? My laptop hit 90% recently, and rather than start randomly deleting things or looking at disk space applications. I went looking for what was actually taking up room. A good chunk of it turned out to be buried in a few hundred .terraform directories. Every terraform init you run downloads a complete copy of every provider your project uses and drops it inside that working directory. Run it in enough projects and you end up storing the same few hundred megabytes over and over.

This one is specific to the machine you work on. Build agents get a clean workspace every run so they never accumulate anything, but a laptop you have been running Terraform on for a couple of years is a different story.

Where the Space Actually Goes#

Provider binaries are big, and they have been getting bigger.

These are the unpacked sizes on darwin_arm64 as of this week:

ProviderVersionUnpacked
hashicorp/aws6.33.0739 MB
azure/azapi2.10.0334 MB
hashicorp/azurerm4.76.0218 MB
purestorage-openconnect/cbs0.11.249 MB
hashicorp/vsphere2.4.031 MB

The AWS provider is 739 MB. That is a single file.

terraform init writes a fresh copy of it into .terraform/providers/ for every project that references it. Add a second provider, which almost every one of mine has, and you are carrying most of a gigabyte per working directory before you have written a line of HCL.

I counted the directories on my machine that contain .tf files and came up with 143. Multiplying that out by which providers each one uses:

ProviderProjectsDuplicated
hashicorp/aws2920.9 GB
hashicorp/azurerm5411.5 GB
purestorage-openconnect/cbs582.8 GB
azure/azapi31.0 GB
hashicorp/random410.7 GB
vmware/vsphere180.5 GB
37.4 GB

The unique bytes behind all of that come to 1.39 GB.

Everything else is the same providers written to disk again and again. AWS and azurerm alone account for 87% of it.

On a desktop with a big disk you would never notice. On a work laptop where the internal drive is whatever you were issued, 37 GB is the difference between having room for a lab VM and not.

That number is a floor, not a ceiling.

It assumes one version of each provider per project. terraform init -upgrade leaves the old version sitting there next to the new one, and nothing cleans it up.

Finding Out What You Have#

Before changing anything, go and look. This walks your code directories and totals up what the .terraform folders are holding:

find ~/Documents ~/Projects -type d -name '.terraform' -not -path '*/.git/*' 2>/dev/null \
  | tee /tmp/tfdirs.txt | wc -l
du -sch $(cat /tmp/tfdirs.txt) | tail -1

To see the worst offenders:

du -sh $(cat /tmp/tfdirs.txt) | sort -rh | head -20

The Fix#

Terraform has had a shared provider cache for years. It is not on by default.

Create ~/.terraformrc:

plugin_cache_dir   = "$HOME/.terraform.d/plugin-cache"
disable_checkpoint = true

Then create the directory, because Terraform will not create it for you and silently ignores the setting if it is missing:

mkdir -p ~/.terraform.d/plugin-cache

From then on, terraform init downloads each provider version once into the cache and symlinks it into the project instead of copying:

.terraform/providers/registry.terraform.io/hashicorp/azurerm/4.76.0/darwin_arm64
  -> ~/.terraform.d/plugin-cache/registry.terraform.io/hashicorp/azurerm/4.76.0/darwin_arm64

Existing projects keep their local copies until you clear them out. To reclaim that space, delete the provider directories and re-init:

find ~/Documents -type d -name '.terraform' -not -path '*/.git/*' -exec rm -rf {} +

Nothing in .terraform is precious. It is all rebuilt from your lock file on the next init.

Your state is a different matter, which I will come back to.

Proving It Worked#

I re-inited three projects after turning the cache on. Here is what they take up now against what they would have without it:

ProjectOn diskWithout cache
deploy-cirrus-source-vm0 B31 MB
azure/610x8 KB279 MB
azure/ec-native-example8 KB552 MB

862 MB of providers reduced to 16 KB of symlinks!

They all point at one 861 MB cache that every other project shares as well.

I left one older project alone as a control.

It was inited before I set any of this up and still holds a real 20 MB copy of its provider. That is what every one of those 143 directories used to look like.

What the Cache Does Not Fix#

The cache still accumulates versions. Mine is already holding azurerm 4.76.0 and 4.73.0 side by side, 431 MB between them, because I ran -upgrade at some point. Terraform never prunes it. The difference is that it happens once globally now instead of once per project, so clearing it out occasionally is a single command:

rm -rf ~/.terraform.d/plugin-cache && mkdir -p ~/.terraform.d/plugin-cache

Do not put this in CI. The cache is not safe for concurrent use, and parallel init runs can corrupt it. Build agents get a clean workspace every run anyway, so there is nothing to gain.

One more thing worth knowing: you will see plenty of guides telling you to export TF_PLUGIN_CACHE_DIR instead. Both work. The env var only applies to shells that have it set, which is how you end up wondering why your editor’s integrated terminal behaves differently. The .terraformrc file applies everywhere.

Dealing With State#

Providers are where the disk space is. State is where the risk is.

If you are already cleaning up, it is worth doing both.

Find what is sitting on your laptop:

find ~/Documents -name 'terraform.tfstate*' -not -path '*/.terraform/*'

Local state means the record of what you have deployed exists in exactly one place, on one machine, with no locking and no history.

I moved everything to remote backends a while ago. For Azure that is a storage account:

terraform {
  backend "azurerm" {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "sttfstate"
    container_name       = "tfstate"
    key                  = "ec-native-example.tfstate"
  }
}

Run terraform init -migrate-state and Terraform copies the existing state up and asks before switching. Once it is confirmed in the backend, the local file is safe to delete.

The space you get back from this is measured in kilobytes. That is not the point.

State now lives somewhere backed up and locked, and clearing out .terraform directories stops being something you have to think twice about.
