Deploying Azure Red Hat OpenShift with Terraform

September 9, 2026 · 7 min read · 1297 words
Share

Are you looking for a way to deploy Azure Red Hat OpenShift without clicking through the portal every time? ARO is an Azure resource like anything else, which means Terraform can manage the whole cluster lifecycle. I will get a cluster deployed into an existing VNet, and cover the two things that will stop your apply cold if you have not hit them before.

Why Terraform for ARO#

Azure Red Hat OpenShift is a managed OpenShift service. Microsoft and Red Hat run the control plane, the worker nodes land in your own VNet, and the whole thing is exposed as an Azure resource. The azurerm provider has a first-class resource for it, so there is no need to drop to the CLI or the azapi provider for the cluster itself.

I have been building this out for a lab where the cluster needs to be reproducible, which means every dependency has to be in code: the subnets, the route table associations, and the cluster. Getting there took a couple of failed applies, mostly for reasons that were not obvious from the error messages.

In Part 2 I will cover attaching enterprise block storage to the cluster with Everpure Cloud.

Prerequisites#

Before running any of this, make sure you have the following in place:

  • An existing VNet with room for two new /27 subnets
  • A service principal with Contributor on the subscription
  • The Microsoft.RedHatOpenShift resource provider registered
  • Terraform installed locally, or a Terraform Cloud workspace
  • Enough vCPU quota in the region for the control plane and workers

Register the resource provider with the Azure CLI if you have not already:

az provider register --namespace Microsoft.RedHatOpenShift

Project Structure#

I keep the same layout I use for every Azure Terraform project:

aro/
├── backend.tf              # Terraform Cloud workspace
├── providers.tf            # azurerm
├── variables.tf            # every input, typed and described
├── terraform.auto.tfvars   # values (gitignored)
├── subnets.tf              # the two ARO subnets
└── aro.tf                  # the cluster itself

Get one thing right before you write a line of HCL: terraform.auto.tfvars belongs in .gitignore. The service principal secret lands in that file, and so does the Red Hat pull secret if you use one. Neither belongs in git history.

terraform.auto.tfvars

Configuring the Provider#

Nothing surprising here:

terraform {
  required_providers {
    azurerm = {
      source = "hashicorp/azurerm"
    }
  }
}

provider "azurerm" {
  features {}
  subscription_id = var.subscription_id
}

Creating the ARO Subnets#

ARO needs two empty, dedicated subnets in an existing VNet, one for the control plane and one for the workers. They cannot be shared with anything else, and they have to exist before the cluster is created.

A /27 is enough for each in a lab. Size the worker subnet for how far you plan to scale, because you cannot resize it later without rebuilding the cluster.

data "azurerm_virtual_network" "core" {
  name                = var.vnet_name
  resource_group_name = var.vnet_resource_group
}

resource "azurerm_subnet" "aro_master" {
  name                 = "aro-westus2-master"
  resource_group_name  = var.vnet_resource_group
  virtual_network_name = data.azurerm_virtual_network.core.name
  address_prefixes     = ["172.17.56.0/27"]

  private_link_service_network_policies_enabled = false
}

resource "azurerm_subnet" "aro_worker" {
  name                 = "aro-westus2-worker"
  resource_group_name  = var.vnet_resource_group
  virtual_network_name = data.azurerm_virtual_network.core.name
  address_prefixes     = ["172.17.56.32/27"]

  private_link_service_network_policies_enabled = false
}

That private_link_service_network_policies_enabled = false line is required on the control plane subnet. ARO puts a private link service in front of the API server, and Azure will not allow that while network policies are enforced on the subnet.

If you route egress through a firewall or an NVA with user-defined routing, associate the route table to both subnets:

resource "azurerm_subnet_route_table_association" "aro_master" {
  subnet_id      = azurerm_subnet.aro_master.id
  route_table_id = var.route_table_id
}

resource "azurerm_subnet_route_table_association" "aro_worker" {
  subnet_id      = azurerm_subnet.aro_worker.id
  route_table_id = var.route_table_id
}

Make that route table ID a variable. My first version had the full ARM resource ID inline with the subscription ID baked into it, which meant the configuration only worked in exactly one subscription.

Without a route table, ARO defaults to sending egress out through the worker nodes and an Azure Standard Load Balancer. That is fine for a lab. For production, user-defined routing through a firewall is the better path.

Deploying the Cluster#

The azurerm_redhat_openshift_cluster resource covers everything. Here it is with a private API server and private ingress:

resource "azurerm_redhat_openshift_cluster" "aro" {
  name                = var.cluster_name
  location            = var.location
  resource_group_name = var.resource_group
  tags                = var.tags

  cluster_profile {
    domain                      = var.domain
    version                     = var.aro_version
    managed_resource_group_name = var.cluster_resource_group
  }

  network_profile {
    pod_cidr     = var.pod_cidr
    service_cidr = var.service_cidr
  }

  main_profile {
    subnet_id                  = azurerm_subnet.aro_master.id
    vm_size                    = "Standard_D8s_v6"
    encryption_at_host_enabled = true
  }

  worker_profile {
    vm_size      = var.worker_vm_size
    disk_size_gb = var.worker_disk_size_gb
    node_count   = var.worker_node_count
    subnet_id    = azurerm_subnet.aro_worker.id
  }

  service_principal {
    client_id     = var.sp_client_id
    client_secret = var.sp_client_secret
  }

  api_server_profile {
    visibility = var.api_visibility
  }

  ingress_profile {
    visibility = var.ingress_visibility
  }
}

A few notes on the values.

managed_resource_group_name is the resource group ARO creates and owns for the cluster infrastructure. It has to be a group that does not exist yet, and you should not put anything else in it.

pull_secret is optional. The provider accepts one in cluster_profile, but if you leave it out ARO uses a default and you skip storing a large Red Hat credential in your Terraform state. I leave it out unless I need registry access the default does not cover.

pod_cidr and service_cidr default to 10.128.0.0/14 and 172.30.0.0/16. Check those against your existing address space before you apply, because they cannot overlap with the VNet.

The default worker size is small. I started on Standard_D4s_v6 and scaled the node count up, and the first ceiling I ran into was not CPU, it was the network bandwidth on the worker VMs. If you plan to push throughput through the cluster, size the workers for the bandwidth rather than the vCPU count.

Two outputs are worth exporting so you can get into the cluster afterwards:

output "aro_console_url" {
  value = azurerm_redhat_openshift_cluster.aro.console_url
}

output "aro_api_server_ip" {
  value = azurerm_redhat_openshift_cluster.aro.api_server_profile[0].ip_address
}

Deploying the Configuration#

The usual cycle:

terraform init
terraform plan
terraform apply

Give the apply plenty of time. An ARO cluster takes somewhere in the range of 30 to 45 minutes to come up, and the Terraform run will sit there for all of it.

Once it finishes, pull the cluster credentials:

az aro list-credentials --name <cluster-name> --resource-group <resource-group>

Then log in with the console URL from the output, or with oc:

oc login <api-server-url> -u kubeadmin -p <password>

Two Things That Will Block Your Apply#

Azure Policy fighting the CoreOS workers. My first apply failed and the error told me almost nothing useful. The cause was a policy assignment called “Configure periodic checking for missing system updates on Linux azure virtual machines”, which was forcing patch assessment mode onto the ARO worker nodes. ARO runs RHEL CoreOS and manages its own node lifecycle, so guest patching and guest configuration policies that target Linux VMs will fight it.

If your subscription inherits a policy set from a management group, go check for VM patching and guest configuration assignments before you spend 40 minutes waiting on a failed apply. Scoping an exclusion to the ARO managed resource group is the cleanest fix.

The subnets have to be genuinely empty. Not mostly empty. ARO refuses a subnet that has any existing resource in it, and the error does not spell that out. If you are carving subnets out of a VNet that has been in use for a while, double check nothing has a NIC parked in there.
